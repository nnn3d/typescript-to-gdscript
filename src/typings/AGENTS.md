# Typings generation notes

Edge cases for Godot class typings, scene typings, addon typings and `typings-overrides/`. The project overview is `PROJECT.md` at the repo root.

- `export class`: enables module augmentation for scene typings (named exports, not default)
- `[__parent]` encoding: `Node<Tree extends object = any>`, conditional type `[any] extends [{[__parent]: infer P}] ? P : Node` — `any` default → `unknown` → returns `Node`
- GodotResources `.gd`: `typeof _Class` (class/constructor type), not instance type
- GodotResources `.tres` / `.res` with a script on its `[resource]` root: `_GDGetInterfaceResource<GodotScripts, "<script path>", <header type>>` (`resource-types.ts`), the instance type of that script — looked up by PATH, as scene nodes are. Not by the header's `script_class="X"` (Godot 4.7 does write it): a bare `X` in `_resources.d.ts` resolves only under `generateGlobalClassTypes`, a script without `class_name` has none, and a header goes stale until Godot re-saves the file. The helper is generic on purpose: the same conditional on concrete types (`"res://x.gd" extends keyof GodotScripts ? GodotScripts["res://x.gd"] : R`) does not narrow, reports TS2538 inside the generated file and types the entry as `any`. It also falls back to the header when the script does not extend it (a stale path). Pinned by `sword.tres` / `loot.tres` (named / anonymous) and `Armory.ts` in `tests/typings/scene-typings`
- Script keys are the res:// path of the CONVERTED `.gd` (`tsScriptResPath`: `gdDir` + the path under `tsDir`), because that is what a `.tscn` attaches. They used to be the path under `tsDir` alone, which matched only when `gdDir` is the project root — every typings test used that layout, while `tstogd init` writes `src/` → `scripts/`, so in the default layout a scene's `get_node` stayed `Node | null` in its own script. `tests/typings/script-res-paths.test.ts` pins the init layout, full and incremental (`generateFileTypings` now takes `gdDir`)
- Cross-file class visibility: `import { Name as _Name }` + `declare global { class Name extends _Name {} }`
- TileMap embedded scenes: sub_resource chains (TileMap → TileSet → TileSetScenesCollectionSource) parsed via `collectTileMapScenes()`, injected into `instancedParents` in Pass 3 of `generateTypings()` with `NodeType<{[__parent]: grandparentAlias}>` for proper chain resolution (e.g. `TileMap<{[__parent]: _Level}>` so `get_parent().get_parent()` resolves correctly). For root TileMap in instanced scenes (e.g. TilesetObjects.tscn), grandparent is resolved from instancing scenes.
- Operator symbols use `__ops_` prefix: `__ops_add`, `__ops_sub`, `__ops_mul`, `__ops_div`, `__ops_rem`, `__ops_eq`, etc.
- Godot XML `Type[]` suffix (e.g. `Node[]`) handled by `godotTypeToTs()` → `Array<Node>`
- Scene tree `__node_extends` circularity avoided: unique name `%X` entries skip self-reference on the unique node itself
- `_GDTreeHandlers` does NOT include `/root/` overloads (only in module augmentation) to avoid per-TreeNode evaluation overhead
- `collectAllSignalHandlers()` pre-parses all scenes once for batch signal resolution (vs per-file `resolveSignalHandlers()`)
- Class-level enums → `namespace ClassName { const enum EnumName { ... } }` in .gd.d.ts for strong type checking
- Class-level inner classes → `namespace ClassName { type InnerClass = InstanceType<typeof ScriptClass.InnerClass>; }` in .gd.d.ts
- `gd.as` variant conversion to `Array` constrains source via `T extends { [__variant_converts]: any } & Array[typeof __variant_converts]` — source must be in Array's own variant_converts union. Element type extracted from `[Symbol.iterator]` of source. Plain `never` return gets silently swallowed by TS method bivariance in large interfaces, so this constraint-based approach is used instead
- `addons/` directory excluded from user file discovery (findTsFiles, findGdFiles, findSceneFiles, watcher); addon `.gd` files discovered separately via `findAddonGdFiles()` for `generate-addon-typings`
- Addon output is declarations only — no `.ts` is written to the typings tree, and therefore no `// @ts-nocheck` (there are no bodies left to fail strict checks) and no need to exclude `types/addons` from the user tsconfig. This is not optional tidiness: TypeScript resolves `./my_script` to `my_script.ts` in preference to `my_script.d.ts`, so a converted source sitting beside its declaration would shadow it entirely
- Declaration emit does not discard the types a GDScript author never wrote — it **freezes** them. `func describe():` with no return annotation still emits `describe(): string`, because TypeScript infers from the body before dropping it. The one thing that degrades is parameters: a method parameter has no contextual type to infer from, so `func _physics_process(delta):` emits `delta: any` — the implicit any a consumer already saw. `tests/fixtures/addon-declarations/` pins what comes out for the common shapes
- The freeze is relative to what the programs saw at generation time, and the addon cache keys on the addon files alone. So a change OUTSIDE `addons/` that addon types depend on — the Godot typings (`generate-gdscript-global-typings`), a project script an addon extends or uses, the tsconfig — is not noticed by a cache hit, and neither are the warnings replayed with it: an addon extending a project script that didn't exist yet keeps `_base: Resource` and its TS2507 after the script is added. The remedy is documented rather than automated: `clear-cache`, or `convert --no-cache` (which does bypass the addon cache). `PACKAGE_VERSION` covers `tstogd` updates. Fingerprinting the project's declarations into the key was considered and declined: the project's own `.gd.d.ts` change with its scripts, so the addon cache would miss on almost every run, while addons that depend on project code at all are rare
- **`.gd.d.ts` are generated into the temp tree, beside the `.ts` they describe, before the ts-helpers and the emit, and copied to `outputDir` only afterwards.** They declare the addon classes globally and populate `GodotResources`, and that is the only way one addon's reference to another resolves — by class name or through `preload("res://addons/…")`. Without them in the program the nullable helper infers against whatever an earlier run left in the typings folder (the same input then gave `Node` on a first run and `Node | null` on the second), and every cross-addon `preload` freezes as the `Resource` fallback. It is also what makes `extends "res://x.gd"` sound: GD→TS renders it as `extends preload(...)`, which declaration emit can only express as `declare const X_base: <type of the expression>` — `typeof DemoBase` when the path is in `GodotResources`, otherwise `Resource`, which is not a constructor (TS2507). Co-locating works because the temp tree mirrors the output layout exactly, so the same extensionless `./my_script` resolves to the `.ts` in temp and to the `.d.ts` in the typings tree. A `.gd.d.ts` is copied out only when its declaration was emitted: otherwise it would import a file that isn't there, and under `skipLibCheck` the global class it declares would silently become `any`
- **Which tsconfig files a program over addon code takes** is one rule, `addonProgramRoots(outputDir, targets)` (`src/typings/addon-output.ts`), built once in `generateAddonTypings` from the run's expected output and passed to both the ts-helpers and the emit: the project's `.d.ts`, minus the addon output being rebuilt. That output has to stay out for two reasons. It is the previous run's result, which would stand in for the temp files being rebuilt; and for declaration emit it is the very set of files being written — TypeScript refuses to write a file that is also one of its inputs (TS5055). What counts as that output is decided by ORIGIN, as for the sweep: the run's own targets plus anything with the generator marker. A hand-written declaration in `<typingsDir>/addons` stays in, or every addon that uses it would infer `any` against it. Taking `.d.ts` only is for cost: the declarations still pull in the few project sources addon types actually reach. No root filter can keep out a file that is IMPORTED, though: a project `.d.ts` outside the addon folder importing an addon declaration by path pulls it back in, the emit yields nothing, and the sweep then removes the old copy — so output alternates between runs. `emitAddonDeclarations` reads `program.getOptionsDiagnostics()` for TS5055 and reports it with that explanation (the emit result alone says nothing)
- `emitOverrides` sets `rootDir` / `declarationDir` even though the write goes through a `writeFile` callback: references between files _inside_ the temp tree are written relative to where TypeScript believes the output lands, so without them a sibling `preload()` emits as `typeof import("../../../../../<abs path>/helper")` instead of `typeof import("./helper")`. It also neutralises user settings that would suppress or redirect the emit: `noEmitOnError: false` (the converted code never type-checks cleanly), `isolatedDeclarations: false` (it refuses to emit any declaration with an inferred type — every one worth having here), and clears `outFile` / `incremental` / `composite`
- **No path into the temp tree may survive into a declaration**, and three layers see to it. (1) `typeTextForSource` (`src/converter/gd-to-ts/helpers/type-text.ts`): every ts-helper that writes a type into the source (`ready-field-types`, `extends-type`, `implicit-null-return`) renders it through this, because `checker.typeToString` names a type with no name in scope by an ABSOLUTE module path — `import("C:/…/Temp/tstogd-addon-…/helper")._$CLASS$_`. Declaration emit then reuses that specifier for every other reference to the same module, so one such annotation spoiled the whole declaration (even `const Helper` beside it), with zero diagnostics; the old in-place `.ts` made it harmless, the temp tree made it a broken file. The same text in migrated user code tied the file to one machine. (2) `reanchorSpecifierTransformer` (an `afterDeclarations` transformer) rewrites specifiers so they hold at the declaration's location: a relative one that leaves the temp tree (an addon extending a project script, whose class lives in the user's `src/` — TypeScript writes it relative to the temp _source_) and an absolute one, which TypeScript itself writes when no relative path exists (temp and project on different Windows drives); one pointing into the temp tree is mapped to the same file in the output. It replaces only the string literal, via `visitEachChild`, to stay clear of node-factory signatures that shift across the supported TypeScript range (`updateImportTypeNode` among them). (3) The `writeFile` callback checks the final text for the temp dir and, if it's there, reports a diagnostic and marks the run degraded. Pinned by `tests/fixtures/addon-declarations/anonymous-preload-consumer` — a class-named provider would not have caught it, which is how the first version shipped
- **Diagnostics.** Per emitted file only `emitResult.diagnostics` is read: it already carries that file's declaration diagnostics, and asking `getDeclarationDiagnostics` as well reported each one twice. Those catch what cannot be _written_ as a declaration; `validateAddonDeclarations` type-checks the result and catches what emits cleanly but doesn't check. It runs after the `.gd.d.ts` reach `outputDir`, so the `declare global` addon classes are in the program and cross-file references don't report spurious TS2304; it forces `skipLibCheck: false`, because everything it checks is a declaration file and a user's `skipLibCheck: true` would silently turn the pass into a no-op; and it is skipped without a tsconfig, where it could only restate the "no tsconfig" warning. When the Godot typings aren't visible to the tsconfig it returns **one** configuration diagnostic instead of dozens of TS2304s blaming the addon; the probe is whether `Node` resolves to a declaration _outside_ the default library, since `lib.dom` declares a `Node` of its own. Emit diagnostics name temp files, so `relocateDiagnostic` maps them to the addon's `.gd`, dropping line/column (they belong to the converted code). All addon diagnostics are `severity: 'warning'` and deliberately excluded from `hasReportableErrors` — the user cannot fix third-party code, and one malformed addon must not block their build. They print under an `ADDON` group (`DiagnosticSource`) from `convert` (also under `--no-check`: they come from typings generation, not the check), `initial-convert-gd-to-ts` and `generate-addon-typings`, and through the watcher's log
- **Stale output is swept on every call** (`sweepAddonOutput`) — on a full run, on a cache hit, and when no addons are left at all. Generated files in `<typingsDir>/addons` that the run didn't produce (or, on a cache hit, doesn't expect) are deleted, and emptied folders with them. The case that matters is upgrading from a pre-declaration tstogd, which left `<name>.ts` in the typings tree: it wins module resolution over the `<name>.d.ts` beside it and would silently pin the user to stale addon types, and no hash of the declaration can reveal it — hence the sweep on the cache fast path
- **The sweep deletes by origin, never by extension.** A file is removed only if its first line carries a generator marker: `// AUTO-GENERATED` (the `.gd.d.ts` generators already write it; emitted `<name>.d.ts` get `GENERATED_HEADER` prepended in the `writeFile` callback) or `LEGACY_SOURCE_HEADER` (what pre-declaration versions wrote atop the converted `.ts`). A hand-written declaration in that folder must never be deleted (it is overwritten only while its addon is still generated). `site/src/content/docs/guide/addons.md` has users move an addon's typings out of the folder BEFORE excluding the addon: excluding first turns the generated files stale, and the next run deletes them. Symlinks are skipped, not followed. When `<typingsDir>/addons` overlaps the addon _source_ folder (`typingsDir` set to the project root) the sweep refuses to run at all: the addon's own files live there and a marker isn't a strong enough guarantee to delete among them
- **Cache.** The fast path requires every current `.gd` to be fresh AND no entries for `.gd` files that are gone (`hasAddonEntriesOutside`): freshness is all-or-nothing because one addon's types depend on another's, and a removal changes that resolution exactly as an addition does. A **degraded** run records nothing and drops the addon entries — no tsconfig, typings not visible, a temp path in the output, a declaration missing for a reason outside the addon's code (TS5055, say), or a diagnostic that belongs to no addon script — because a cache hit would keep serving that output after the user fixed the cause. What is the addon's own is cached, since it never goes away: its warnings are stored on the entry of the script they belong to (`AddonEntry.diagnostics`) and replayed on a cache hit; and a script TypeScript wrote no declaration for because of an error in its own code (it writes none that has errors — TS4094 and the like) is recorded with `declHash` / `dtsHash` `null`, fresh while both files stay absent. Declining to cache either would switch the addon cache off for good; caching a warning silently would hide it
- How declarations spell a `preload()` result is TypeScript's choice, and it is left alone on purpose. `preload<P>(path: P): GodotResources[P]` is resolved the moment `P` is a literal, so the lookup never reaches the declaration — only its result, named by the shortest name visible from the `.d.ts`: a global name when there is one (`typeof NamedHelper` for a `class_name`, `Texture2D` for an asset), otherwise the exporting module (`typeof import("./helper")._$CLASS$_` for a script without `class_name`), and `Resource` from the fallback overload when the path isn't in `GodotResources`. Rewriting the `import(...)` form to `GodotResources["res://…"]` / `GodotScripts["res://…"]` was considered and declined: the types are identical for consumers (checked), and it would only change the spelling
- Addon declarations freeze types that depend on the consumer's scenes. `get_node("Child")` inside an addon resolves through that addon script's scene typings, which the addon pipeline doesn't see, so it emits as `Node | null`; the addon cache doesn't track scene typings either. Before, the body was re-typed in the consumer's program on every load
- Without a tsconfig the declarations are knowingly degraded (a warning says so, and the run isn't cached): besides `any`, a `get_node(...)` return can leak an unbound type parameter (`_GDGetNode<…, P>`), because the `.gd.d.ts` overloads reference helper types that don't resolve
- Pass 2 (`scanTsFilesForClasses`) scans the converted `.ts`, not the emitted `.d.ts`, even though the declaration is what consumers see. On `extends preload(...)` the declaration's base class is the synthesised `_ExtendsPath_base`, which would make `extendsNode` — and with it the typed `get_node` / `get_parent` overloads — come out wrong
- `createTsProgram({ includeFilesAsRoots })` adds `files` as extra program roots alongside the tsconfig's own set. Off by default, and it must stay that way: with a tsconfig the config's file set _is_ the program, and every other caller passes files that set already covers. The addon pipeline needs it (temp sources are outside the project and nothing imports them), and `runTsHelpers` turns it on whenever it is given `extraFiles`, since asking for extra inputs and getting a program without them would be a silent no-op
- Global enums keep their Godot spelling. `generateGlobalScopeDeclaration` groups `globalEnums` by the part before the dot: an undotted name stays a top-level `declare const enum Key { ... }`, a dotted one becomes `declare namespace Variant { const enum Type { ... } const enum Operator { ... } }` — enums sharing a prefix merge into one namespace block. The registry has always stored the dotted names (`Variant.Type`), and GDScript accepts `Variant.Type` in both type and value position, so the flattened `Variant_Type` was the odd one out: `gdTypeToTs` passes a GD annotation `Variant.Type` straight through, which used to name a type nothing declared. `buildGlobalEnumMap` (`src/converter/gd-to-ts/context.ts`) dropped its matching `replace(/\./g, '_')` — bare `TYPE_INT` now qualifies to `Variant.Type.TYPE_INT`. No converter change was needed in either direction: `classifyTypeReferenceName` already returns the name verbatim for anything `registry.isGlobalEnum()` knows
- `godotTypeToTs`'s dotted branch distinguishes the two kinds of enum reference, and must do it on the WHOLE name: a global enum (`Variant.Type`) keeps its spelling, a CLASS enum (`Node.ProcessMode`) becomes `int` (its members are emitted as `static readonly ...: int`), and anything else becomes `unknown` rather than a dangling dotted name. Discriminating on the prefix does not work — `Variant` is itself a documented class (`typings/classes/Variant.d.ts`), so a prefix test maps `Variant.Type` to `int`. `TypeContext.globalEnumNames` carries `@GlobalScope`'s enum names for the check, from the same source the registry reads for `globalEnums`, so the two agree by construction. The branch is currently unreachable from Godot's XML (enum-typed params and returns are documented as plain `int` with a separate `enum=` attribute); `tests/typings/type-mapping.test.ts` covers it directly
- `gd.as` takes `abstract new (...args) => U` rather than `new`, so an abstract class of the user's own is a legal cast target (a concrete constructor satisfies `abstract new` too). It also carries scalar overloads for `int` / `float` / `bool` / `String` / `StringName`, mirroring the `gd.is` set — `x as int` and friends are ordinary GDScript casts, verified against Godot. Those return the scalar rather than narrowing the source: `int` and `float` are both aliases of `number` here, so the type argument cannot narrow the result the way a class type can. Godot's own engine classes are NOT emitted `abstract`, so the `abstract new` change is about the user's TS classes, not the typings
- `get_node` / `get_node_or_null` / `has_node` each carry a `NodePath` overload alongside the string ones — Godot's own parameter type for all three, and the idiomatic GDScript spelling. A `NodePath` VALUE carries no literal for the scene-tree lookup to match, so the overload answers the untyped `Node | null` / `boolean`. It has to be emitted in three places, not one: `typings/globals/globals.d.ts` (`_GDTreeHandlers`) and BOTH sites in `content-generators.ts` — the per-script module augmentation, and the `declare global { class X extends ScriptClass }` shadow, where the declarations HIDE the inherited overloads rather than merging with them
- `globals.d.ts` declares `var Promise: PromiseConstructor` with an EMPTY `PromiseConstructor`. With `noLib`, TypeScript needs a global `Promise` value to infer an `async` function's return type; without it, calling an `async` method that has no written return type reports TS2468 + TS2705 (only on call, because the return type is inferred lazily). Keep the interface empty: GDScript has no Promise object, so `new Promise(...)` / `Promise.all(...)` must stay type errors. Both declarations are `@deprecated`, which strikes through a bare `Promise` value but not `Promise<T>` in type positions. Pinned by `run_all` in the `await-coroutines` fixture
- `Signal` has a PRIVATE `then` (in `typings-overrides/signal.d.ts`) whose only job is typing `await signal`: TypeScript reads `then` for `await` regardless of access, while private keeps `.then(...)` a type error and out of autocomplete. It resolves to what Godot 4.7 returns (verified headless): `null` for `[]`, the value for `[A]`, the tuple for more (an `Array` at runtime). Godot counts the arguments the emit PASSED, not the ones declared (`signal tick(when: int)` + `tick.emit()` awaits to `null`), so optional elements give a union: `_GDSignalEmits` in `globals.d.ts` expands the tuple into every argument list it allows before mapping each one (`[a: int, b?: String]` → `int | [int, String]`). Unknown arity (an array type such as `gd.signal<unknown[]>()`; `gd.signal()` itself defaults to `[]`, no arguments) is detected with `any[] extends T`, not `T['length']` — the typings' Array has no `length`. The helpers live in `globals.d.ts` because an override can only add class members. ACCEPTED GAP (user decision, 2026-09-30): TypeScript unwraps thenables repeatedly, so `await f()` where `f(): Promise<Signal<[int]>>` is typed `int`; Godot gives the Signal object when `f` paused before returning, and the value only when it did not. TS cannot express a single unwrap, the pattern is rare, and the alternative (no `then`) mistypes every plain `await signal`. Pinned by `returns_signal` in `signals.ts`; documented in `site/src/content/docs/reference/transform-rules.md` Pinned by `tests/typings/type-checks/signals.ts` and `wait_for_damage` in the `await-coroutines` fixture
- Godot `call` / `bind` / `callv` on a function-typed value are typed by `CallableFunction` (`typings-overrides/callable-function.d.ts`): the function's own parameters and return, `bind` from the end. TypeScript only consults `CallableFunction` under `strictBindCallApply`; with it off, every function type falls back to the untyped `Function` surface (`typings-overrides/function.d.ts`, `call(...args): unknown`). The projects have `noLib`, so `fn.call(x)` never means JavaScript's `this`-binding call — only the typing degrades. `site/src/content/docs/reference/configuration.md` asks a non-strict project to keep `strictBindCallApply: true`, and the converted-project test (`tests/converter/fixtures-gd-to-ts-project.test.ts`) runs that way (`strict: false` + `strictBindCallApply: true`); the gd-to-ts `lambda` fixture's `call_lambda` fails the test without the flag
- `Signal.connect` carries Godot's real signature: `connect(callable, flags?: int): int` (`typings-overrides/signal.d.ts`). Without `flags` there was no way to pass `Object.ConnectFlags` at all. The callback deliberately stays a concrete function type instead of widening to `Callable` — `type Callable = Function`, so a union with it accepts any function and the parameter list stops being checked; a bound callable needs no widening because `CallableFunction.bind` returns a proper function type with the bound arguments removed
- `parseClassXml`'s `<member>` and `<signal>` patterns keep their attribute run **lazy** (`[^>]*?`). Greedy, the run reaches the `>` that ends the tag and the following alternation is tried from there: the `\/>` branch fails and the `>body</member>` branch succeeds by matching across the _next_ tag, swallowing it whole — alternation is tried before the run gives the `/` back, so backtracking never rescues it. The greedy form lost 90 members across 60 classes (`TextureRect.stretch_mode`, `Control.mouse_filter`, …). The signal pattern additionally has to allow attributes after `name` (`deprecated`, `experimental`). `tests/typings/godot-registry.test.ts` pins both shapes
- `StringName` is a type alias for `String` (`type StringName = String`) — identical API in GDScript, no separate interface needed
- `NodePath` is its own variant type with a dedicated interface and constructor (not mapped to `string`). Has `[__variant_converts]` for `gd.as()` support
- Operator overload types: `OPERATOR_OVERLOAD_TYPES` hardcoded set removed; now uses `registry.hasOperators(typeName)` to derive from the registry at runtime
