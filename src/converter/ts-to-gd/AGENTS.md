# TS → GD converter notes

Edge cases and design decisions for `src/converter/ts-to-gd/`. Rules shared with GD → TS are in `src/converter/AGENTS.md`. The project overview is `PROJECT.md` at the repo root.

- Numeric literals: use `getText()` to preserve `100.0` (TS parser strips trailing `.0`)
- String literals: use `getText()` to preserve escape sequences
- Dict string keys: use `emitStringLiteral()` for proper quote escaping (`'it\'s'` → `"it's"`)
- Object shorthand properties keep their identifier as a string key and pass the value through `emitExpression`. Value lookup uses the shorthand value symbol, so `{ GodotObject }` keeps the key but emits `Object` as its value. A local binding with that name remains unchanged.
- Own-class member access (`src/converter/ts-to-gd/own-class-ref.ts`): `ClassName.X` and `this.X` on the enclosing class have three possible GD spellings and none is valid everywhere — `ClassName.X` works in every context and resists shadowing but needs a `class_name`; `self.X` is instance-only (`self` is a **parse error** inside `static func` and resolves to `Nil` inside a `static var` initializer, failing at runtime instead of at parse time); a bare `X` works anywhere inside the class body but loses silently to a local/param of the same name. So the class name is preferred, `self.` is the anonymous-class fallback in instance context, and bare the fallback where `self` doesn't exist. `resolveOwnClassRef` returns a three-way `OwnClassRef` union — `prefix` (the text to put before the member, `''` for the bare form), `fallthrough` (not an own-class ref, emit normally), `unsupported` (no valid spelling; the caller raises an `error`). Two cases are `unsupported`, both of which would otherwise ship silently-wrong GD that Godot accepts: (1) an **inner class reaching an outer member of an anonymous script class** — both fallbacks resolve inside the body they sit in, so `self` is the inner instance and the bare name is out of scope; (2) a **bare form shadowed by a local/param** (`isShadowedByLocal` walks params, block `var`/`let`, `for` initializers, catch clauses, nested function/class declarations, and destructuring patterns, stopping at the class boundary; it ignores declaration order deliberately — over-reporting costs a rename, under-reporting ships a misread). `isStaticContext` walks the AST upwards to the enclosing member (no transformer state), passing **through** lambdas — a GD lambda captures `self` lexically just like a TS arrow, so a lambda inside a `static func` is still static context. `this` in instance context deliberately returns `fallthrough` ("nothing special") so the `.get()` rewrite downstream still gets its chance. For `this` the name comes from the **enclosing** class, not `currentClassName`: inside an inner class `this.Q` in a `static func` must be `Inner.Q`. The `_Name` anonymity rule applies to the script class only — an inner class is declared with its name verbatim. Type positions (`s: MyClass.State` → `s: State`) go through `tsTypeNodeToGdType` and never reach this module. **Emitting `ClassName.X` created a new dependency on Godot's global class cache** that `self.X` never had: the cache is only populated by an import pass, and `validateGdFiles` runs `--check-only` without one, so a freshly generated or just-renamed script reported `Identifier not found: <ClassName>` against correct code. `isUnindexedOwnClassFalsePositive` + `collectDeclaredClassNames` (`src/godot-validate/error-parser.ts`) suppress it, scoped to `class_name`s declared by the files under validation so a real typo still surfaces; both the parsed-error filter and the unparsed-output fallback apply it
- Lambdas (`src/converter/ts-to-gd/lambda.ts`, split out of `expressions.ts`, + `reserveBlock` / `writeLine` in `src/converter/ts-to-gd/emitter.ts`): a block-body arrow is one expression that needs LINES, which an expression emitter building a string cannot write. It used to return the header (`func(x):`) alone and leave the body to the caller, and only two callers knew to ask for it — a variable initializer and a class field. Those are the positions where the lambda happens to be LAST on its line; in every other one (call argument, array element, dict value, `return`, assignment RHS, default parameter value, nested lambda) the body was silently dropped and the output was a `func(x):` Godot cannot parse — issue #8 case 1. Now `emitLambda` calls `emitter.reserveBlock(() => t.visitBlock(body))`, which registers the body and returns a `\0block:N\0` marker to leave in the string; `writeLine` expands it: text before the marker, then the body one indent deeper (run through `visitBlock`, so its statements keep their own source-map positions and can raise their own diagnostics), then whatever followed the lambda on its own line at the BODY's indent. The two positional call sites and the `isBlockLambda` / `emitLambdaBody` delegate methods are gone, so every position gets the same treatment and the tail-position output is byte-identical to before (nothing follows the marker, so no continuation line is added and `writeLine` skips its own newline). The body indent is the emitter's `indentLevel + 1` — NOT the visual indent of the line the marker sits on. Verified against Godot 4.7: a continuation must land on an indent level the parser still has open, so a second sibling lambda whose body sits one level deeper than the first (`f(func(): …, func(): …, 5)`) gives "Unindent doesn't match the previous indentation level", while all bodies in one statement at the same level parse and run correctly — including inside a multi-line dict, where the body then sits at the same column as the entry line, and in a default parameter value, where it sits at the same column as the function's own body. The `\0` marker cannot arrive from source: string literals are emitted from `getText()`, so a `\0` escape in TS stays the two characters `\` and `0`, and a real NUL inside a literal is left alone (it splits into one part and the expansion loop never runs). A marker whose block was never reserved throws rather than emitting a body-less header. The mirror case is checked too: `assertBlocksDrained`, called at the end of `transform()`, throws when a block was reserved but its marker never reached `writeLine` — a lambda body that vanished with nothing to show for it. That is why `emitCallExpression` now tries the `gd.*` helpers BEFORE emitting arguments: those helpers re-emit their operands from the AST, so emitting the arguments first left a second, orphaned reservation behind. **A lambda used as an operand is parenthesized** (`standsAlone` in the same module): a GD lambda body runs to the end of the expression, so `func(): f() if c else g` is ONE lambda whose body is the conditional — verified at runtime, the converter's ternary output was silently returning a Callable instead of choosing between two. `standsAlone` lists the SAFE parents (call/new argument, array element, property assignment, variable/field/parameter initializer, `return`, expression statement, arrow body, `=` RHS — transitively, so `a = b = () => x` is covered — and already-parenthesized; `as`/`satisfies`/`!`/`<T>` are erased so they recurse to their own parent) and parenthesizes everywhere else; the list is the safe side, because a redundant pair of parentheses costs nothing and a missing one ships a different program. `,`, `)` and `]` are what make the safe positions safe: they cannot continue an expression, so the lambda body stops there (confirmed with Godot's arity check, which sees 2 arguments in `f(func(): g(), 5)`). `ExpressionStatement` covers a bare `() => {};`. That is NOT diagnosed: Godot rejects it itself (verified 4.7: `Standalone lambdas cannot be accessed. Consider assigning it to a variable.`) and the emitted lambda means what the TypeScript meant, so per AGENTS.md rule 11 it is a Godot error rather than the converter's to report — `STANDALONE_LAMBDA_ERROR` and its converter-diag fixture were removed; there is no behaviour left to test. An IIFE goes through the generalised `.call()` rewrite below. Pinned by `tests/fixtures/ts-to-gd/lambda-positions.{ts,gd}` (every position, plus nested lambdas, a default parameter value and a block lambda as a ternary operand — the three shapes that exercise `writeLine` reentrancy and the indent rule), which the Godot-validate runner parses for real, and by unit tests in `tests/converter/emitter.test.ts` for the two cases no fixture reaches: a marker with no reserved block, and a NUL that is not a marker.
- Calling a Callable VALUE (`src/converter/ts-to-gd/callable-call.ts`): GDScript calls a NAME — a method, a global function, a constructor. It cannot call what an expression produced: `f()()`, `a[0]()`, `(c)()`, `(func(): …)()` all fail with `Cannot call on an expression. Use ".call()" if it's a Callable.` The converter used to rewrite to `.call()` only when the callee was an IDENTIFIER declared as a variable or parameter, so every other shape shipped a `.gd` Godot refuses to parse, silently. `isCallableValueCall` splits the question by whether the callee is a NAME at all (identifier / property access / `super` — judged on the LAST step only, so `f().m()` and `Foo.new().m()` are fine). A non-name callee is ALWAYS `.call()` and needs no type: TS calling something that is not a name is calling a value, and a function value is a `Callable` — there is no second reading, which is why `(x as any)()` and `d["fn"]()` convert rather than error. A name can be either, so there the rewrite still has to be earned: the type carries a call signature (and no construct signature) and the callee does NOT resolve to a `MethodDeclaration` / `MethodSignature` / `FunctionDeclaration` / **ambient `VariableDeclaration`**. That last one is the value types: the typings spell all 30 of them `declare const Vector2: Vector2Constructor`, which carries call signatures, no construct signature, and a declaration kind otherwise identical to a local holding a lambda — so without it every `Vector2(x, y)` in a typings-loaded project emitted `Vector2.call(x, y)`, which Godot rejects. The rule is that an ambient `declare const` creates no variable in the emitted script, so there is nothing there for a `Callable` to live in; `isAmbient` lives in `src/converter/common/gd-names.ts` and is shared with the annotation classifier and the getset fallback. Import aliases are followed, so a helper imported from another file is judged by its declaration. The call-signature requirement is what keeps an UNRESOLVED name (missing typings) a plain call instead of a guessed `.call()`. This also fixed a fixture that had been pinning runtime-broken output: `dict.gd` expected `h.fn()` for a Dictionary entry holding a Callable, which parses but dies with `Invalid call. Nonexistent function 'fn' in base 'Dictionary'` — Godot-validate only parses, so it could never catch it. It is now `h.fn.call()`, verified by running it. Pinned by the `call_values` and `untyped` cases in `tests/fixtures/ts-to-gd/lambda-positions.{ts,gd}` (IIFE, call result, array element, ternary, `as any`, dictionary index — all executed against Godot 4.7). A member reached through `self` or the own class name is settled by its DECLARATION instead, via `isCallableMemberCall` in the same module: a class member that is not a method is a field, a getter or a property signature, and all three hold a value. The type cannot answer it there — the dialect's `Callable` is `type Callable = Function`, an interface with no call signature — which is why the earlier `ts.isPropertyDeclaration` test missed an accessor and emitted `self.cb()` for a getter returning a `Callable` (Godot parses it and dies with `Invalid call. Nonexistent function 'cb'`). When nothing resolves there is no declaration to read and it falls back to the type-based test, so an unresolved name is still left alone. `super.m` stays on the NAME side and must remain there: unlike every other base, `super` cannot yield a `Callable` at all — Godot 4.7 rejects `super.m.call()` with `Expected "(" after function name`. Pinned by `accessor_values` in the same fixture.
- `void` has no value (`src/converter/ts-to-gd/void-value.ts`): GDScript rejects taking the result of a call to a function that returns nothing ("Cannot get return value of call to \"f()\" because it returns \"void\""). One rule, keyed on `ts.TypeFlags.Void`, three consequences. (1) Where the position lets the `return` be DROPPED, it is rewritten: an arrow's expression body becomes the lambda's only statement (`func(p): self.apply(p)` — issue #8 case 3), and a `return <void call>;` statement becomes the call followed by a bare `return` (the `return` stays, since it may be an early exit). (2) Where something READS the value — a variable initializer, an argument, an operand — there is nothing to rewrite to, and that is NOT diagnosed. `var x = f()` on a `void` function is a Godot parse error (verified 4.7: `Cannot get return value of call to "side()" because it returns "void"`), and the emitted GDScript still means what the TypeScript meant — a Godot error, not a semantic divergence, so per AGENTS.md rule 11 it is Godot's to report. `checkVoidCallUsedAsValue` / `isVoidCallValueDiscarded` / `VOID_CALL_AS_VALUE_ERROR` were removed along with the enumerated list of discarding positions, which had already produced one false positive: it compared the call against the arrow's `body` slot instead of the outermost erased wrapper, so `(p) => (this.apply(p))` was rejected outright. Note TypeScript does not catch this either — `const x = f()` where `f(): void` is legal TS (`x` is typed `void`); only a concrete incompatible parameter type (`takesInt(f())`) raises TS2345. Godot is the only check, and that is by design. The `void-call-as-value` converter-diag fixture went with it — there is no diagnostic left to pin. The REWRITES are still pinned, by `tween_expr` (arrow body) and `early` (`return`) in `tests/fixtures/ts-to-gd/lambda-positions.{ts,gd}`, which the Godot-validate runner parses for real. (3) The `void` OPERATOR is an error everywhere (`VOID_OPERATOR_ERROR`) — issue #8 case 2. Its result is `undefined`, which the dialect has no representation for, so there is no position where the value can be emitted, and accepting it only where the value is discarded would be the positional special case Rule 12 rejects; with (1) in place it is not needed for the callback shape it was being used for. Pinned by the `void-operator` converter-diag fixture.
- Abstract functions (`visitMethodDeclaration` in `src/converter/ts-to-gd/class-members.ts`): an `@abstract` function emits its SIGNATURE ONLY — no trailing `:`, no body. Verified against Godot 4.7: a `pass` body gives "An abstract function cannot have a body" and a bare trailing colon gives "Expected indented block after function declaration"; signature-only (and the inline `@abstract func …` form) are accepted. TS guarantees an `abstract` member has no body, so nothing is dropped
- `switch` → `match` (`src/converter/ts-to-gd/switch.ts`): the dialect is "a `switch` IS a `match`" — branches never fall through, so a non-empty clause running into the next is the normal way to write independent branches and is NOT diagnosed; TS7029 (`noFallthroughCasesInSwitch`) fires on exactly that shape and nothing else — not on stacked clauses, not on a breakless last clause, not on a clause ending in `return` — so it fires on essentially every `switch` in the dialect. It is deliberately NOT filtered: it is off by default and not part of `strict`, so it only appears when the user turned it on, and the noise sets exist for diagnostics that cannot mean anything here — ones our own generated typings provoke (TS2434/2435/2449) and ones enforcing a JS runtime rule GDScript lacks (TS2377/17009) — not for overruling a compiler option the user chose. Documented as "keep it off" instead. Four parts. (1) **Stacking**: consecutive clauses with an EMPTY `statements` list are collected and emitted as one branch whose patterns are comma-joined — the shape `emitSimpleMatchAsSwitch()` (GD→TS) produces, so the round-trip closes. A run containing a `default` collapses to `_` alone, since the wildcard already subsumes the other patterns. A run with no body to stack onto (trailing empty clauses) emits `pass`. Before the stacking fix each clause became its own branch and the empty ones got `pass`, silently returning `null` from a stacked `case` — issue #7. (2) **`break`**: `unlabeledBreakTarget()` resolves a `break` the way TypeScript does (nearest enclosing loop or switch, stopping at a function boundary). One resolving to the switch is an `error` — GDScript has no branch-exiting jump, and dropping it is only behaviour-preserving in tail position (`if (x) break; print(y);` would start running `print`), so it is rejected outright rather than dropped in some positions and not others. Breaks resolving to a loop **inside** a case are emitted normally — emitting them as GD `break` would exit that loop's ENCLOSING loop, which is why depth-blind filtering is wrong. It still emits nothing, so `emitStatements()` writes `pass` (an unfilled body is a GDScript parse error) for the `--emit-on-error` output. Reported from `visitStatement`, on the `break` itself, NOT from a walk over the whole `switch`: `addDiagnostic()` writes its `# ERROR:` marker at the emitter’s CURRENT position, and from `visitSwitchStatement` that position is still above the `match` line — every marker stacked there, detached from the branch it belonged to. Visiting reaches each `break` exactly once anyway, since the only clauses whose statements go unvisited are the empty ones stacked onto a following body. Marker placement is pinned by `tests/fixtures/ts-to-gd/unsupported-body.{ts,gd}` (`switch_break_marker`); the diagnostics themselves by the `switch-break` converter-diag fixture. Whether anything was emitted is read back off the emitter (`mark()` / `hasCodeSince()`), not predicted from the AST: a statement emits nothing for many reasons — a `break` bound to a `switch`, a clause-less `switch`, a type-only declaration (a body-level `type` alias or `interface`, erased silently by `visitStatement` the same way `file-scope.ts` and the namespace walk erase them at their levels; before that branch existed the rule held at two scopes out of three and a body-level one hit the catch-all as `Unsupported statement: TypeAliasDeclaration`), an unsupported construct leaving only an `# ERROR:` marker — and the predicate that enumerated them went stale as soon as a new kind appeared. `hasCodeSince()` treats three kinds of line as not-code, which is exactly GDScript's own rule for filling a block: blank, comment, and a bare annotation (one with nothing after it on the line — an annotation attaches to the statement that follows, so `@export var x = 1` fills a block and a lone `@warning_ignore(...)` does not). The `BARE_ANNOTATION` regex runs its argument list to the LAST `)` on the line, not the first: an argument is free-form text (it reaches the emitter through `gd.eval`) and may contain `)` inside a string, and the failure modes are asymmetric — matching too eagerly costs a redundant `pass`, matching too little suppresses one and emits a block Godot refuses to parse. `@export var x = 1` still fails to match either way, because text is left over after the closing `)`. A nested `Block` statement flattens into the body around it (GDScript has no bare block) but emits its own comments, and deliberately does NOT apply a `pass` fallback — that call belongs to the body it flattened into. That machinery — `unlabeledBreakTarget()`, `isLabeledJump()`, `isSwitchBreak()`, `emitStatements()` — lives in `src/converter/ts-to-gd/statement-body.ts`, which imports neither `statements.ts` nor `switch.ts`, so both can use it without a cycle. **Labels**: `LabeledStatement` and any `break`/`continue` naming a label are both an `error` (shared `LABEL_ERROR` message), and the labeled statement's body is deliberately NOT visited — emitting the loop inside without its label would look like a successful conversion of something that is not one. The jump check exists even though it is unreachable through a well-formed program (TS requires the label to be in scope, so the `LabeledStatement` is rejected first): `unlabeledBreakTarget()` answers `undefined` for a labeled `break`, which is the same answer it gives for one binding to nothing, and that answer is what makes `isSwitchBreak()` false — i.e. "emit a plain `break`", which would bind to the NEAREST loop rather than the labeled one. Reading the label off that `undefined` would be wrong, so `isLabeledJump()` checks it directly and `visitStatement` tests it before either jump case. Pinned by `tests/converter/statement-body.test.ts` (unit) plus the `labels.{ts,json}` converter-diag fixture. `emitStatements()` VISITS every statement (no-code ones emit nothing but still get to report why — that is how a `break` bound to the switch still gets its diagnostic) and appends `pass` only when the whole run emits nothing. Every GDScript body routes through it: `visitBlock` / `visitStatementBody`, match branches, `gd.match` `do` bodies, and both accessor forms (`class-members.ts`, `gd-getset.ts`) — the last two previously iterated `body.statements` by hand and emitted a body-less `get:` / `set(v):` for an empty accessor. GD→TS matches the dialect: `emitSimpleMatchAsSwitch()` emits no `break;`, and gives a branch with no STATEMENT a `{}` block so it does not stack onto the next case. Keyed on the EMITTED TEXT (`hasTsStatement()` — any line that is neither blank nor a comment), the same rule `hasCodeSince()` applies in the other direction, and for the same reason: a `pass`, a comment, an annotation and a rejected construct that leaves only an `/* ERROR: … */` marker all produce text without producing a TS statement, and the earlier AST-keyed predicate (`bodyHasStatement()`, which listed `Comment` / `PassStatement` / `Annotation`) missed the marker case — a branch whose `break` was rejected went out as a bare `case 1:` and stacked onto the branch below, merging two branches into one with NO diagnostic on the return leg. `hasTsStatement()` strips `/* … */` spans BEFORE the per-line scan: only the first line of a block comment starts with `/*`, so a line check alone reads the rest as statements — a GDScript branch holding nothing but a multi-line `"""..."""` (a statement there, a comment in TS) lost its `{}` and merged into the branch below, with no diagnostic on either leg. The strip can reach too far — a `/*` inside a string literal opens a span that closes at the next `*/` — and that is the safe direction, the same asymmetry `BARE_ANNOTATION` has: removing text can only cost a redundant `{}`, where missing one merges two branches. The shapes live in the `tests/fixtures/gd-to-ts/match.{gd,ts}` pair (`test_bodyless_branches`: comment-only, `pass`-only, annotation-only, multi-line-block-comment-only, then a real branch) and their TS→GD mirror in `tests/fixtures/ts-to-gd/match-stacked.{ts,gd}` (`blocked_empty_case`), so each leg is pinned by the normal fixture runners. One round-trip test in `tests/converter/gd-to-ts.test.ts` drives off that same `match.gd` and pins the COMPOSITION, comparing branch structure rather than full text — a full-text round trip is not achievable by design, since the converters normalise indentation, rewrite `x is not T` to `not (x is T)`, drop `: Variant`, and turn a field `x` into `self.x`. GD→TS transcribes sections in SOURCE order, `_` included, with no diagnostic and nothing dropped — even though `_` matching first makes every branch below it dead in the GDScript. That is deliberate: this output is migration output, read and edited by a human, so losing code silently is worse than carrying a branch that never ran, and reordering would hide what the source said. Normalising `default` to last belongs to the other direction, which does it (part 3). The two directions therefore do NOT compose for this shape: `match x: _: "o"; 1: "one"` (always `o`) comes back as `match x: 1: "one"; _: "o"` (`one` for `x == 1`). Accepted — it only bites code whose branches were already dead, and the migration pass is where a human is meant to resolve it. (3) **`default` position**: `default` becomes `_`, which matches everything, so GDScript reaches a branch written below it only if there is none — it MUST come last. The run holding `default` is therefore emitted last and the rest keep their relative order (two complementary `filter()`s over the collected runs, so the reordering is one stable split rather than a sort). Moving it preserves meaning rather than changing it: TS tests every `case` label before falling back to `default`, wherever `default` sits, so branch position carries no information. A run's leading comments travel with it, since `emitMatchBranch()` emits them — with `statementsAllowed: false`, because they land in the PATTERN section, above the `1:` line, where GDScript takes no statement. That flag only changes the `/* */` substitution: the normal one is `"""..."""`, a string EXPRESSION, and a bare string in pattern position parses as a pattern and swallows the branch's `:` ("Expected \":\" or \"when\" after \"match\" patterns"). Comment-only positions get `#` per line instead (`*` margin and outer blank lines stripped, as the `##` path does), which is a comment wherever it is written. `#` and `##` needed no change. Pinned by `comment_between_branches` in `match-stacked`, which the Godot-validate runner parses for real. A comment AFTER the last clause's statements is leading trivia of the case block's `}` — no clause below it to carry it — so `visitSwitchStatement()` hands that `}` to whichever run ended the SOURCE, wherever the reordering put that run (`trailing_comment_in_case` in `match-stacked`). This replaced an `error` on every clause after `default`'s run (`reportUnreachableAfterDefault()`, deleted) — erroring was safe but rejected code that is perfectly meaningful in the dialect. A `default` stacked INTO a following body (`case 1: default: body`) is one run and moves as a unit. Godot itself would NOT catch a misplaced `_`: a branch below it is unreachable but perfectly well-formed, so the engine imports it silently — which is why the converter has to handle the position itself rather than let the build surface it. `tests/fixtures/ts-to-gd/match-default-not-last.{ts,gd}` pins the reordered output, one method per shape: `default` first, `default` inside a run of empty clauses (the run moves as a unit), a `default` whose whole run is empty (already last, nothing to move), and a `default` carrying a leading comment (which moves with it). There is no converter-diag fixture for this any more — there is no diagnostic left to pin. (4) **Patterns**: case expressions go through `emitMatchPatternExpr()`, not `emitExpression()` — Godot accepts only a constant, identifier or `A.B` in pattern position, so an own field sheds its `self.` prefix (same rule as `gd.match`). It is called with `wildcardUndefined: false`, which is the ONE part of the `gd.match` pattern language a `switch` label does not inherit: `gd.match` spells its wildcard `undefined` (that is what GD→TS emits for `_`), but a case label is an ordinary TS expression, where `undefined` is restricted like anywhere else. Mapping it would have emitted `_` for `case undefined:` — a catch-all wherever the user wrote it, making every branch below it dead, and swallowing the ``undefined` is restricted; use `null`` error `emitExpression()` raises. The flag propagates into nested array/dictionary patterns for the same reason. Pinned by the `undefined-to-null` converter-diag fixture (`in_case`). A clause-less `switch` emits nothing at all — `match x:` with no branch under it does not parse — and is NOT diagnosed: it is dead code either way, and saying so is the type-checker's job, not the converter's. The value being switched on is dropped with it.
- Match patterns (`emitMatchPatternExpr` in `src/converter/ts-to-gd/gd-match.ts`): Godot accepts a bare identifier as a pattern unconditionally, but accepts an attribute access (`self.X`, `MyClass.X`) ONLY when it resolves to a constant. So an own-class access whose symbol declaration is a `ts.PropertyDeclaration` (a plain field → GD `var`) sheds its prefix and emits the bare member name, while enum members and namespace `const`s keep theirs and stay shadow-proof. Probed against Godot 4.7: `self.State.IDLE` (enum) ACCEPTED, `self.VAR_FIELD` REJECTED, bare `VAR_FIELD` ACCEPTED, `MyClass.VAR_FIELD` REJECTED ("Cannot find member"). Note the check keys off the declaration kind, not the emitted text — the same kind of declaration test the Callable `.call()` rewrite uses
- `gd.getset` TS7022 avoidance: the helper's `get`/`set` are strictly typed (`(() => T) | null` / `((v: T) => void) | null`) so bodies get full type checking. The inline bodies reference `this.<name>` (the property being defined), which triggers `TS7022` unless the property has an explicit type annotation. Non-function `get` types like `any` or `unknown` would avoid TS7022 but lose body type checking, so the converter always emits the annotation instead. Attempts at `NoInfer<T>`/`() => any`/`() => NoInfer<T>` all still trigger TS7022 because TS enters the closure for binding-analysis regardless of generic-inference flags.
- TS-to-GD `gd.getset` type resolution order (in `visitGdGetsetProperty`):
  1. Explicit `gd.getset<T>({...})` type argument
  2. Property declaration's own annotation (`name: T = ...`) — primary source in practice
  3. `set` callback parameter type (via `checker.getCallSignatures()` on `setExpr`) — fallback for inline `(v: int) => ...` or function-refs `this.set_x`
  4. `value` expression's type — numeric literals inspect raw source text to distinguish `int` (no decimal) from `float` (with decimal); other expressions go through `checker.getTypeAtLocation` + literal-widening + primitive mapping (`number`→`float`, `string`→`String`, `boolean`→`bool`)
- TS-to-GD setget: accessor pairs are grouped by name in `visitClassDeclaration` (new `'accessor'` OrderedMember kind), then emitted via `visitAccessorPair()` as a single `var X: get: ... set(v): ...` block (missing half is synthesized with a passthrough default). `PropertyDeclaration`s whose initializer is `gd.getset<T>({...})` route through `visitGdGetsetProperty()` which detects inline vs function-ref form and emits the appropriate GDScript, raising errors for mixed or incomplete configs. Inside accessor bodies, `this.<accessorName>` is rewritten to a bare identifier via `currentAccessorName` tracking (avoids infinite recursion in generated GDScript).
- `gd.getset` nullability: the type requires both `get` and `set` keys but each may be `null`. `null` means "use GDScript's default (backing-field read/write)" — the TS→GD converter simply omits that accessor from the GD setget clause. Both-null is an error ("at least one of `get` or `set` must be non-null"). GD→TS always emits both keys explicitly, using `get: null` / `set: null` when only one side is present in the source GDScript.
- `gd.eval` space indentation: converts space-based indent to tabs by tracking space→depth mapping; mixed tabs/spaces is an error
- `gd.eval` as variable initializer: `processGdEval()` returns processed lines with relative tab depth; `visitVariableStatement` emits first line as `var X = <firstLine>`, remaining lines are emitted at current indent (their embedded `\t` prefixes act as additional relative depth beyond the var line)
- TS-to-GD `/** */` doc comments → one `##` line per SOURCE line (`emitLeadingComments`), not one `writeLine` holding newlines: GDScript has no multi-line comment, so every line after the first would land at column 0 with no `#` — ending the block it was written in, and (in a body holding nothing else) reading as a statement to `hasCodeSince()`, which suppressed the `pass` that body needed. The per-line `*` strip is `^[ 	]*\*[ 	]?`, horizontal space only: `\s` matches a newline, so a line holding nothing but `*` ate the break after it and pulled the next line up, collapsing a blank line — a paragraph break in a Godot doc comment — into nothing. Pinned by `tests/fixtures/ts-to-gd/comments.{ts,gd}` (`documented`) and, for the `pass` interaction, `match-stacked.{ts,gd}` (`doc_comment_only_if`)
- TS-to-GD `/* */` non-doc block comments → `"""..."""` (single-line and multiline); class-level trailing comments emitted via closing brace
- Plain-object member access → `.get()` auto-conversion: property/element access checks the OBJECT type via `isPlainObjectType()` (`src/converter/ts-to-gd/access-rewrite.ts`) — all non-nullish union constituents must be structural object types that are not classes, not Godot registry types (classes/constructors/global enums — value types like `Vector2` are interfaces in our typings but have no `.get()` at runtime), not arrays/tuples, not callable, not explicit `Dictionary`/`TSOnly`, not enums/namespaces. Standalone READS rewrite to `.get(...)`; skipped for: assignment targets (`obj.prop = v` / `+=` / `++` — `obj.get("p") = v` is invalid GD; `isAssignmentTarget()` walks parens/non-null wrappers), chained property access (`obj.prop.inner`, inner link only — the FINAL read still rewrites), call expressions (`obj.prop()`), and class field access. Legacy fallback: on non-plain-object types the rewrite still fires when the member type includes `undefined` (via `typeContainsUndefined`). Mixed/unprovable types (any/unknown/error, type params, intersections) fall back conservatively to dot access.
- `gd.as` / `gd.is` grouping (`groupCast` in `gd-cast.ts`, split out of `gd-helpers.ts` for the 500-line cap; `emitOperand` there also serves `gd.ops`) follows the two operators' real precedence, which sits at opposite ends of GDScript's table — verified at runtime. `is` binds tighter than everything except `.`, `[]` and `()` (`y and x is int`, `false == x is String`, `not x is String`, `"a" if y else x is String` all group `x is T` first), so it is grouped ONLY as a receiver (`x is T.m` reads the dotted part as a type path). `as` binds looser than everything except assignment and takes the whole expression to its LEFT as the value — `count / total as float` is `(count / total) as float` (0.0 for 1 and 2 where the TS meant 0.5), `w if c else v as int` casts the ternary — so it is bare only in a slot delimited on both sides (`isDelimitedSlot`: an initializer, return, expression statement, call/`new` argument, array element, dict value, element-access index, assignment right-hand side, a statement condition, a template span) and grouped everywhere else. The list is an allowlist on purpose: a redundant pair of parentheses is never wrong, a regrouped cast is silent. Position is read through `effectiveNode`, past the wrappers the emitter erases — `gd.as(n, T)!.texture` is the form `strict` makes users write, and reading `node.parent` directly missed it — and source parentheses count as grouping (`isSourceGrouped`), since the emitter writes them back out. An earlier version grouped both operators only as receivers and documented the operand position as safe; that was checked for PARSING only, on the left operand.
- Operator spelling (`src/converter/ts-to-gd/operator-tokens.ts`, split out of `expressions.ts`): `binaryOperator` returns null for an operator GDScript lacks (`>>>`, `&&=`, `||=`, `??`, the comma operator) and `emitBinaryExpression` reports it. It used to fall back to `??` without a diagnostic, and was missing six compound assignments GDScript does have (`&=`, `|=`, `^=`, `<<=`, `>>=`, `**=` — verified at runtime), so `k |= 2` came out `k ?? 2`. `emitIncrement` owns `++` / `--` on both sides: `x += 1` / `x -= 1` where the value is discarded (an expression statement, a `for` incrementor), an error anywhere else, since GDScript's `+=` is a statement. "Discarded" looks through parentheses and erased wrappers, and a statement or `for` incrementor is emitted without them (`withoutOuterWrappers`) — `(this.n++);` goes out as `self.n += 1`, since GDScript refuses an assignment in parentheses. A rejected operator or a `++` used as a value leaves `null` next to its `# ERROR:` marker, so `--emit-on-error` output still parses (pinned in `unsupported-body`). The prefix form used to go through `unaryOperator`, whose default emitted nothing, so `++this.n` became `self.n`. Pinned by `operators` (`test_compound_assignment`) and the converter-diag `unsupported-operators` fixture
- Operands a helper splices into an operator it builds itself — each `gd.ops.*` operand, and the VALUE of `gd.as` / `gd.is` — go through `emitOperand` (`gd-cast.ts`), which parenthesizes anything `splicesUnsafely` flags: binary and ternary expressions, a template literal (emitted as `"" + str(a) + …`), `gd.as` / `gd.is` calls, every prefix operator (`!` is emitted as `not`, which binds looser than comparison; `-`, `+`, `~` bind looser than `is`, so `gd.is(-a, int)` emitted bare read `-(a is int)`), and a lambda, whose body runs to the end of the line (`gd.as(() => a, Callable)` emitted bare cast the `a` inside it). They are call ARGUMENTS on the TS side, so the source needs no parens around them and no `ParenthesizedExpression` reaches the emitter to preserve; that is why plain TS binary expressions are safe and these are not. `splicesUnsafely` looks through the erased wrappers first (`gd.as(n, float)!` emits exactly what `gd.as(n, float)` does) but not through parentheses, which survive. The value side matters for `is`, which binds tight: `gd.is(c ? a : b, float)` emitted as `a if c else b is float` tested only `b`. `gd.ops` needs no result-side equivalent: `emitOpsHelper` wraps every result, the unary `plus` / `minus` included — those used to go out bare, and `gd.ops.minus(v).length()` emitted `-v.length()`, a negated length where the TS meant the length of `-v` (both type-check, so nothing noticed); pinned by `operators` (`flipped_length`) and `type-casting` (`negative`, `wrapped`). It already wrapped every binary result
- The class header emits `class_name` BEFORE `extends` (`emitClassHeader`), the order Godot's own GDScript style guide prescribes: `@tool`/`@icon`/`@static_unload` → `class_name` → `extends` → doc comment. Godot accepts either order, so this is style, not correctness. GD→TS reads both — `scanScriptClassHeader` classifies by neighbour KIND (`ExtendsStatement` / `ClassNameStatement`), never by position
- TS parameter properties (`constructor(public x: int)`, any accessibility modifier or `readonly`) are REJECTED (`reportParameterProperty` in `class-members.ts`), one error per parameter. GDScript has no such construct, and the dialect does not desugar TS syntax GDScript lacks — destructuring is rejected the same way although it too spells out mechanically. Before this they went out silently as plain `_init` arguments, with no field and no assignment, so every later `self.<name>` failed in Godot far from the cause. The parameter itself stays in the signature (only its property half has no GDScript form), and the markers are written after `indent()` so they land inside the `_init` body, where the missing assignment belongs; an otherwise empty body still gets `pass`. GD->TS never produces parameter properties (a GD field plus `self.x = x` comes back as a field plus `this.x = x`), so nothing on the return leg depends on them. Pinned by the `parameter-properties` converter-diag fixture (messages, one per parameter) and `unsupported-body` (emitted shape, Godot-validated)
- A property whose type the converter cannot prove is emitted bare — except under a BARE `@export`, where `needsVariantForExport` (`class-members.ts`) fills in `: Variant`. That is the one annotation for which an omitted type is a Godot PARSE ERROR rather than merely an untyped variable (`Cannot use simple "@export" annotation with variable without type or initializer`). Verified against Godot that nothing else needs it: `@export_range`, `@export_enum`, `@export_file`, `@export_node_path`, `@export_storage` and `@onready` all accept an untyped variable, and an `@export` WITH an initializer infers its type. `Variant` is what an untyped GDScript variable already is — Godot's own error for `@export_multiline var x` names the type as "Variant" — so it changes nothing about the program, which is why it is not the kind of guess rule 11 forbids. `@export_multiline` is deliberately NOT covered: it rejects `Variant` outright, so there is no spelling to fill in and Godot's own error stands
- `super` (`emitExpression`, `src/converter/ts-to-gd/expressions.ts`): every use goes out as written, a bare `super(...)` included. Godot's rules, verified against the engine: `super.<name>()` works only when something implements `<name>` (a regular engine method does, `super.get_child(0)`; an engine virtual does not; a SCRIPT ancestor that declares it does, resolving THROUGH intermediate scripts that do not); `super.<property>` is never valid; and a bare `super()` needs some script ancestor to define `_init` — directly under an engine class, or above scripts that define none, it is "Cannot call the parent class' virtual function "\_init()" because it hasn't been defined". All of these are Godot PARSE errors: `--check-only` reports them (so `validate-gd` and the IDE plugin do) before anything runs, whether the base is named by `class_name` or by path. So the converter adds no rule for any of them (AGENTS.md rule 11). Earlier versions did: they reported unreachable `super` members, and dropped a bare `super()` when a walk up the `extends` chain proved an engine base. The drop duplicated Godot's check and could only be as right as the declarations it trusted — a hand-written `.d.ts` without `constructor()` made it skip a script's `_init` silently, and the by-name and `preload(...)` paths disagreed about the same class. GDScript does **not** run a parent `_init` implicitly (verified), so a kept call is never wrong where it is needed, and where it is not, Godot says so at the line. Pinned by `super-engine-base` (a `super()` directly under `Node2D` goes out as written, and the Godot-validate runner's `EXPECTED_ERRORS` asserts Godot rejects exactly that — the old drop fails the fixture), `super-calls` (a constructor without `super()`, an engine method through `super`) and the `super-script-parent` / `super-script-child` / `super-preload-child` / `super-global-child` fixtures, the last through `super-script-parent.gd.d.ts`, a cut-down copy of the generator's global wrapper. The three children (and `extends-path`) extend a sibling, which the Godot-validate runner copies into their project through its `SIBLINGS` map; their output was also run in Godot once and every parent constructor ran.
- Import processing (`src/converter/ts-to-gd/imports.ts`): runs once per file at the top of `transform()`. Builds a `Map<localName, ImportEntry>` keyed by the TS-side identifier; only entries that need a `const X = preload(...)` line OR are candidates for an `extends "..."` rewrite are stored. The map is consulted by `visitClassDeclaration` for the extends rewrite and for field-name conflict detection. Normal projects emit `res://` paths. Projects with `lib: true` emit relative paths only for targets inside their own `tsDir`. Linked package imports map the resolved TS target through that package's `tsDir` and `gdDir`, then emit `res://tstogd_modules/<mount>/<package-relative-gd-path>`, including when the importer is another library.
