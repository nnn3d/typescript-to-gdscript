# Converter notes (both directions)

Conversion rules and edge cases shared by `ts-to-gd/` and `gd-to-ts/`. Direction-specific notes live in each subdirectory's `AGENTS.md`. The project overview is `PROJECT.md` at the repo root.

## Conversion Rules (TS ↔ GDScript)

Each entry reads `TypeScript` → `GDScript` — notes.

- `export class Foo extends Bar {}` → `class_name Foo` / `extends Bar` — One class per file, `export` stripped. `class_name` is suppressed when the TS class name starts with `_` (anonymous convention). `G_`-prefixed names emit verbatim — the `G_` escape from GD→TS is a one-way fallback, not a reversible alias
- `export class _MyFile extends Node {}` → `extends Node` (no `class_name`) — Anonymous-class convention: TS class name `_FilenameInUpperCamel` matches the file basename. GD→TS synthesizes the same name when a `.gd` file has no `class_name`
- `import { Foo } from './foo.ts'` → _(skipped)_ — Non-anonymous + non-renamed → already global in GD via `class_name Foo`
- `import { Foo as Bar } from './foo.ts'` → `const Bar = preload("res://foo.gd")` — Renamed import → preload const so the local alias resolves
- `import { _Anon } from './anon.ts'` → `const _Anon = preload("res://anon.gd")` — Anonymous class → always preloaded since it has no `class_name`
- `extends _Anon` (where `_Anon` is an imported anonymous class) → `extends "res://anon.gd"` — Inheriting an anonymous script requires the path form
- `extends preload("res://some.gd")` → `extends "res://some.gd"` — Direct path-extends form. TS→GD detects the `preload(...)` call shape in the heritage clause and unwraps to the bare GD string-literal extends; GD→TS reverses with `extends preload(...)` so the TS class still has a constructable base
- `import type { … } from '…'` → _(skipped)_ — Type-only imports erased per TS semantics
- `import X from '…'` / `import * as X from '…'` → error — Unsupported — no GDScript equivalent
- `constructor()` → `_init()`
- `this.` → `self.` — Always converted (never stripped) in instance context. Inside a `static` member TS `this` is the class itself and GDScript has no `self` there, so it resolves like `ClassName.` below
- `ClassName.member` (own class) → `ClassName.member` — Emitted as written for a class that has a `class_name`. Anonymous classes (`_Foo`, no `class_name`) have no name to reference, so they fall back to `self.member`, or a bare `member` inside a `static` member where `self` doesn't exist. See "Own-class member access" in `ts-to-gd/AGENTS.md`
- `let` / `const` → `var` — `var` restricted in TS
- `static FOO = ...` → `static var FOO = ...` — Mutable per-class static, shared across instances
- `readonly FOO = ...` → `var FOO = ...` — `readonly` is a **TS-only** contract (compiler-enforced immutability); on the GD side it emits a regular `var` (or `static var` when combined with `static`). Class-level GD `const X = ...` comes from `export const X = ...` inside the paired `namespace ClassName { ... }` block — see "Inner classes" in [transform-rules.md](docs/transform-rules.md#inner-classes-via-namespace-merging)
- `number` → `float` — `int`/`float` type aliases preserved
- `any` / `unknown` / non-class type (alias, `interface`, `object`, unknown name) → (annotation omitted) — GDScript's `Variant` is just "untyped", and the bare `var x` / `func f(x)` / `signal s(x)` forms already express that. `tsTypeNodeToGdType` returns `null` for `any`, `unknown`, and any type reference that isn't a GD type. Classification (`classifyTypeReferenceName` in `src/converter/common/index.ts`): the registry is asked **first** — a Godot built-in recognised by **name** (`hasClass` / `isConstructor` / `isGlobalEnum`) is emitted, but only when the name is not the user's own (no declaration at all, i.e. no typings loaded, or an ambient one — `isUserDeclared` / `isAmbient` in `src/converter/common/gd-names.ts`). That ordering exists because the dialect spells several real GD types as TS aliases (`type bool = boolean`, `type Callable = Function`, `type StringName = String`); asking the alias rule first silently dropped every `bool` / `Callable` / `StringName` annotation in any project that loaded the typings. The gate keeps a user's own `type Color = {...}` dropping rather than claiming Godot's `Color`. Otherwise a name is emitted only if it resolves to a `class`/`enum` declaration (via the checker — covers user `class_name` classes incl. cross-file imports). Everything else — plain interfaces, `object`, `type` aliases, **dotted refs that don't resolve to a class/enum** (`Node.ProcessMode` and the like — the checker returns no declaration and they aren't in the registry, so they can't be verified as real GD types), and **unknown / unresolved names** (typos, bad imports) — is omitted instead of leaking a bogus `: SomeInterface` annotation into the `.gd`. The principle: GD type hints are optional, so the converter only emits a type it can prove and drops everything it can't. `TSOnly<T>` is the explicit opt-out — `tsTypeNodeToGdType` returns `null` for it by name, so a user can keep any type on the TS side and out of the `.gd`. The registry is threaded through `TransformContext.registry`; with no registry the classifier can't recognise Godot built-ins by name, so it emits **only** types it can prove are classes/enums via the checker and drops the rest — omitting is always safe, emitting an unrecognised type would break the GDScript.
- `undefined` → restricted — Use `null` instead
- `===` / `!==` → `==` / `!=`
- `&&` / `||` / `!` → `and` / `or` / `not` — GD returns `bool`, not operand. Non-boolean value use: TS→GD errors, GD→TS wraps in `bool()`
- `cond ? a : b` → `a if cond else b` — TS ternary inverts to GD's value-first form (both directions)
- `for (x of arr)` → `for x in arr` — `for...in` (TS) is rejected — GD `for in` already iterates values
- `super.method()` → `super.method()` — Direct parent-method call, identical syntax
- `super.<sameName>()` → `super()` — TS spells the method; GD's bare `super()` calls the same-named parent method (GD→TS expands to `super.method()`)
- `string` / `boolean` (TS lowercase) → `String` / `bool` (GD PascalCase) — Primitive case normalization; `string` literal types preserve escapes via `getText()`
- `` `${x}!` `` → `"" + str(x) + "!"` — Template literals flattened into `str()`-wrapped concatenation — GDScript has no f-strings
- `switch (val) { case X: ... }` → `match val:` — Simple matches (literal/expression/wildcard patterns, no bindings/guards/array/dict) use native TS `switch`. GD→TS auto-detects via `isSimpleMatchStatement()`. TS→GD: a run of consecutive EMPTY clauses stacks onto the next clause's body as a comma-separated pattern list (`case 1: case 2: return 0` → `1, 2:`), which is the inverse of `emitSimpleMatchAsSwitch()`'s one-label-per-pattern expansion. `break` targeting the switch is an `error` (no GDScript equivalent); so is a `case` after `default`
- `gd.match(val, [...])` → `match val:` — Advanced patterns (bindings, guards, arrays, dicts). Arrow `do: () => {}` preserves `this`; also supports `do()` method syntax
- `get X() {} / set X(v) {}` → `var X: get: ... set(v): ...` — Simple setget: native TS accessors ↔ inline GD get/set bodies. Missing get or set in GD is filled with a passthrough default in TS
- `X = gd.getset<T>({ value?, get, set })` → `var X[: T][ = v]: get: ... set(v): ...` OR `var X: get = fn, set = fn` — Complex setget (has default value or uses `get = fn, set = fn` ref form). Mixing inline + ref forms is an error; both `get` and `set` required
- `//` / `/** */` → `#` / `##`
- `async fn(): Promise<T>` → `func fn() -> T` + body `await` — TS→GD strips `async` and unwraps `Promise<T>` → `T` in `tsTypeNodeToGdType` (`Promise<void>` / bare `Promise` → no return annotation). GD→TS adds `async` when the body has `await`, and wraps the return type in `Promise<…>` (since TS rejects a bare non-Promise return on `async`). Nested lambdas don't lift their `await` to the enclosing function — `containsAwait` stops at `Lambda` nodes so each lambda gets its own async scope. Same wrapping applies to lambda return types.
- `new Foo()` → `Foo.new()`
- `gd.signal<[T]>()` → `signal name(param: T)` — Tuple elements whose TS type resolves to nothing useful (`unknown` / `any` / type alias) emit untyped params (`signal stamina_changed(arg1: float, arg2, arg3)`) rather than `: Variant` — GDScript treats the absence of an annotation as `Variant`, and the bare form carries the same information with less noise.
- `enum X { A, B }` (file scope) → `enum X {A, B}` — Lifted from file scope into the script class. The legacy `static X = gd.enum('A', 'B')` form is rejected by the converter
- `class X { ... }` (file scope, not exported) → `class X:` (inner class) — Lifted from file scope into the script class as an inner class. The legacy `static X = class { ... }` form is rejected by the converter
- `gd.ops.add(a, b)` → `a + b` — Typed operator overloads (also: sub, mul, div, rem, eq, ne, gt, gte, lt, lte, plus, minus)
- `gd.ops.rem(a, b)` → `a % b` — Remainder/modulo for non-number types (Vector2i, etc.)
- `gd.as(val, Type)` → `val as Type` — Class cast + variant conversion (Vector2↔Vector2i, Packed\*Array↔Array) via `[__variant_converts]` symbol
- `gd.eval('code')` → `code` — Raw GDScript passthrough, auto-indented. Also usable as variable initializer (`const v = gd.eval<T>('...')`) — first line becomes RHS, rest is body
- `// @gd.eval: code` → `code` — Magic comment: raw GDScript in any position
- `gd.dict([[k, v]])` → `{k: v}` — Non-string keys
- `gd.typeof(x)` → `typeof(x)` — `typeof` is a TS operator, so the global gets no declaration of its own and lives on `gd` instead. One predicate — `sanitizeFunctionName(name) !== name` plus `registry.isGlobalFunction(name)` — drives all three sites: `generateGlobalScopeDeclaration` skips the declaration, `tryEmitGdUnspellableGlobal` (`src/converter/ts-to-gd/gd-helpers.ts`) unwraps the call, and `emitCall` (`src/converter/gd-to-ts/expressions.ts`) routes the GD call back through `gd.`. Only the `.d.ts` entry is hand-written. Returns `Variant.Type`.
- `/* comment */` → `"""comment"""` — Block comments (also `'''`)
- `int(x)` / `float(x)` → `int(x)` / `float(x)` — Cast functions (also types)
- `StringName('...')` → `&"..."` — `StringName` is a type alias for `String` (identical API)
- `NodePath('...')` → `^"..."` — Own variant type interface + constructor (not mapped to `string`)
- `@exports` → `@export` — Decorators are bare global functions declared in `typings/classes/_globals.d.ts`. The `@exports` plural alias for `export` (reserved in TS) is handled in `src/converter/ts-to-gd/class-members.ts`. **There is no `@gd.export` form** — `gd` holds helpers (signal, getset, match, …) but no decorators. The dead `@gd.<name>` matching code in the converter was removed; `getDecorators()` now handles only the bare-identifier / bare-call shapes.
- `@tool` / `@icon(...)` above `class` → `@tool` / `@icon(...)` above `extends` — Class-level annotations (script-level, not field-level). Both directions: bidirectional via `class-body.ts:emitClassHeader` (TS→GD) and `source-emitter.ts:scanScriptClassHeader` + `classLevelAnnotationNodes` (GD→TS).
- `fn()` where `fn: () => void` → `fn.call()` — Variable-held Callable needs `.call()` in GDScript. Direct method calls (`this.method()`) stay direct. Bidirectional
- `this.get_node("X")` → `$X` / `$"X"` — GD `$` shorthand; GD→TS canonicalizes to `get_node()` so the source map stays accurate. `%UniqueNode` → `this.get_node("%UniqueNode")`
- `let x = 42` (inferred) → `var x := 42` — GD walrus inference; round-trips (TS-side drops annotation when inferred)
- `instanceof` → `is` — Class types (Node2D, etc.)
- `gd.is(x, int)` → `x is int` — Primitive type checks (int, float, bool, String). Negation: `!gd.is(x, int)` ↔ `x is not int`, `!(gd.is(x, int))` ↔ `not x is int`
- `f(a: int, ...args: Array<any>)` → `func f(a: int, ...args: Array)` — Variadic parameters (bidirectional)
- `obj.prop` (plain object type) → `obj.get("prop")` — Member READS on plain TS object types (interface / type literal / object literal — Dictionaries in GD) always auto-convert; also `obj["key"]` → `obj.get("key")`. Skipped for: assignment targets (`obj.prop = v` / `+=` / `++` stay dot — valid on both Dictionary and Object, `obj.get("p") = v` is invalid GD), chained links, callee positions, class fields/instances, Godot registry types, explicit `Dictionary`. Legacy fallback: members whose type includes `undefined` still rewrite on other object kinds. The decision depends only on coarse class-vs-plain-object classification, and `.get()` exists on both Dictionary and Object — so stale outer types cannot produce a silently-crashing access

## Edge Cases

- **Still-open member-name clashes with Godot** (both emit GD that Godot rejects, both derivable from the registry per rule 7, neither diagnosed yet): (1) a class member named after a Godot builtin type (`Color`, `Vector2`, …) — "cannot have the same name as a builtin type"; the `merged-namespaces` fixture works around it by naming its enum `Palette`. (2) a method whose name collides with a NON-virtual inherited method (`call`, `callv`, …) — "The function signature doesn't match the parent" plus "overrides a method from native class" as a warning-treated-as-error; the `functions` fixture works around it by naming its method `invoke_callables`. Note the asymmetry the property check already encodes: overriding an inherited METHOD is ordinary GDScript (`_ready`, `free` are fine — verified against Godot 4.7), so a blanket method-name check would be wrong; telling virtual from non-virtual needs `is_virtual` in the registry data, which `registry-generator.ts` does not currently carry
- Reference-type classification lives in two places that intentionally differ: `isReferenceType()` in `src/converter/common/index.ts` is the canonical registry-only check used at emit time (input: a raw GDScript type string). The typings generator (`src/typings/`) has its own `isNullableGodotType()` in `src/typings/type-mapping.ts` that also consults the derived `valueTypes` / `INTERFACE_CLASSES` sets it builds during generation — those sets don't exist in the converter's runtime context, so duplicating a small amount of logic is preferable to threading the typings `TypeContext` through the converter. Both end up excluding the same things (primitives, value types, enum refs, typed arrays) for the same reasons.
- Inherited-property clash — NOT diagnosed (`reportInheritedPropertyClash` and `GodotClassRegistry.getPropertyNames`, both removed): a field reusing the name of a base-class property is a Godot parse error (verified 4.7: `var paused` on a `SceneTree` subclass → `Member "paused" redefined (original in native class 'SceneTree')`), but NOT a semantic divergence — the emitted `var name` means exactly what the TypeScript meant, and Godot reports the clash itself. Per AGENTS.md rule 10 the converter diagnoses semantic divergences, not Godot errors, so duplicating the engine's check bought little and cost a false-positive risk that blocks valid code. The `inherited-property-clash` converter-diag fixture was deleted with the rule. Methods were never checked either way — overriding an inherited method (`_ready`, `free`) is ordinary GDScript
- Class-level annotations (`@tool`, `@icon`, `@abstract`): GD→TS — `scanScriptClassHeader` walks root-level `Annotation` children and uses `nextNonAnnotationOrComment()` to find the first non-annotation, non-comment neighbour. If that neighbour is `ExtendsStatement` / `ClassNameStatement` (or there's no neighbour at all — trailing-only annotation), the annotation targets the class. `@abstract` is special-cased into `isAbstractClass` / `abstractFunctionIndices` / `abstractClassIndices` (function-target / class-target abstract use the index-returning `indexOfNextNonAnnotationOrComment` so stacked annotations like `@abstract` / `@tool` / `@warning_ignore` / `func` correctly mark the function abstract); other annotations go into `classLevelAnnotationNodes` and render via `emitAnnotationAsDecorator` directly above the `export class` header. Three subtleties matter: (1) **comments are skipped** when classifying — `@tool` / `# note` / `extends` still attaches `@tool` to the class; (2) **`@abstract` uses the same lookahead** as other class-level annotations so ordering between `@abstract` and `@tool` doesn't matter; (3) **defensive flush** of `pendingAnnotations` at the end of `emitScriptClassBody` so any annotation that didn't claim a target is surfaced rather than silently dropped. The blank line between the `export namespace { … }` block and the class is suppressed when class decorators are present (decorators bind tightly to the next declaration in idiomatic TS). TS→GD — `emitClassHeader` calls `getDecorators(node, t)` on the `ClassDeclaration` and emits each as its own line BEFORE the `@abstract` / `extends` / `class_name` lines, mirroring the GD source layout.
- Value types (Vector2, Color, Array, etc.) are instantiated via call syntax `Vector2(1, 2)` — never `new Vector2()`, since GDScript has no `new` for these primitives. Their `*Constructor` interfaces only have call signatures
- Variadic parameters: `func f(a: int, ...args: Array)` ↔ `f(a: int, ...args: Array<any>)`. TS-to-GD: `emitParameters` checks `dotDotDotToken` on rest parameters. GD-to-TS: handles `SyntaxType.VariadicParameter` in `collectParamNames` and `emitParams`.
- TS2377 (`derived constructors must contain a 'super' call`) and TS17009 (`'super' must be called before accessing 'this'`) are filtered by `NOISE_CODES` and `ALWAYS_FILTERED_CODES`, so **`super()` is optional in a constructor**. Both codes enforce a JAVASCRIPT RUNTIME rule — a JS object does not exist until the base constructor has run — and nothing here is run as JavaScript; GDScript's `_init` keeps `self` live throughout and runs a parent `_init` only when the script calls it. They differ from TS7029, which stays visible: that one is a setting the user turned on, these are unconditional, so leaving them would force a meaningless `super()` into every constructor. This is also what makes the GD->TS direction correct: it emits `constructor(...)` carrying whatever `super(...)` the `.gd` had and nothing more, which used to be uncompilable TypeScript (TS2377 + TS17009 on `tests/fixtures/gd-to-ts/constructor.ts`). SYNTHESIZING a `super()` there would have been wrong, not merely noisy — a GD child whose `_init` omits `super()` deliberately does not run the parent's, and adding one changes the program (measured: `hp=100` with the call, `hp=0` without)
- TS2564 (`Property 'x' has no initializer`) is deliberately NOT filtered, unlike TS2377 / TS17009. Those enforce a JS runtime rule GDScript lacks; TS2564 catches a real lie in the type — GDScript starts an object-typed field at `null`, so `target: Node2D` with no initializer claims a node that is not there. It is also governed by a setting the user chose (`strictPropertyInitialization`, part of `strict`), which the dialect does not overrule (the TS7029 precedent). Instead `docs/transform-rules.md` ("Fields without an initializer") teaches the forms that tell the truth, which are exactly what the GD→TS post-pass already emits (`ready-field-types.ts` + `nullable.ts`): `field!: T` when something sets it before use (the editor for an `@export`, an assignment in `_ready`), an explicit default for a value type (`hp: int = 0`, what GDScript uses anyway), and `field: T | null = null` when it may be absent. `!` is erased, so none of them changes the `.gd`. The docs' two `@onready sprite: Sprite2D;` examples used to fail the recommended config; `@onready` exists to defer an initializer, so they now carry one
- The `Object` ↔ `GodotObject` rename (`CLASS_NAME_CONFLICTS`, `src/typings/type-mapping.ts`) is undone on the way to GDScript by `gdClassSpelling()` (`src/converter/common/gd-names.ts`) at every place a class name goes out: type annotations — written ones (`classifyTypeReferenceName`) and the ones `gd.getset` infers from its value (`provableGdType`), both through `engineTypeName()` so they cannot drift; the inferred path used to emit TS's plain `Object` as a GD `Object` hint, which Godot accepts and then refuses at runtime (a Dictionary is no Object) — identifiers in expressions (so `GodotObject.new()`, `is`/`as GodotObject`, `GodotObject.CONNECT_ONE_SHOT`), and `extends` for both the script class (`class-body.ts`) and lifted inner classes (`file-scope.ts`), both through `gdHeritageText()`. `extends Object` itself is an ERROR (`renamedAwayBaseError()`, same file, checked at both heritage sites): the value `Object` is aliased to the engine class, so it type-checks, but its declarations are a `var` and the plain-object interface, not a class, so everything that follows a base by its declaration missed it — the `super()` resolution of the time kept a `super()` Godot rejects. One name per role: `GodotObject` wherever a class is named, `Object` only as a value. GD→TS emits `extends GodotObject` for it (`formatExtendsForTs`). Pinned by the converter-diag `extends-object` fixture and the gd-to-ts `godot-object` fixture. Name resolution everywhere here follows imports via `resolvedDeclarations()` (also `gd-names.ts`). It only applies when the name resolves to the typings' own declaration, so a user class that happens to be called `GodotObject` keeps its name (the `godot-object-user` fixture); the expression path checks the spelling before asking the checker, since identifiers are emitted constantly. Before this, `GodotObject` leaked verbatim and Godot answered `Identifier "GodotObject" not declared`. TS's own `Object` TYPE is the plain-object interface (`typings-overrides/object-dict.d.ts`) — `isRenamedAwayClassName()` keeps it from matching the registry's `Object` by name, so it is dropped like any interface instead of being emitted as the engine class it is not. The VALUE `Object` is `typeof GodotObject` (`declare var Object`), so `Object.CONNECT_DEFERRED` already worked. Pinned by the `godot-object` fixture. GD→TS goes the other way in `gdTypeToTs` (`src/converter/gd-to-ts/type-inference.ts`): its class-name fallback runs `sanitizeClassName`, so GD `Object` in any type position — annotations, returns, params, signal args, and the `Array`/`Dictionary` inners that recurse through it — comes out as `GodotObject` instead of TS's plain-object `Object`; value positions never reach it and keep `Object`. Pinned by the gd-to-ts `godot-object` fixture, which the converted-project check type-checks
- Anonymous-class naming convention: `_FilenameInUpperCamel` (single leading underscore). Helpers `gdFilenameToAnonymousClassName`, `isAnonymousClassName`, `escapeUnderscoreClassName` live in `src/converter/common/index.ts`. The legacy `__CLASS__` sentinel is gone — the GD→TS converter derives the name from `ctx.filePath` and the typings generator emits the actual `_FilenameClass` literal everywhere it used to emit `__CLASS__`. A real GD `class_name _Foo` is escaped to `G_Foo` on the TS side so the underscore-prefix marker stays unambiguous; the escape is **one-way** — TS→GD treats `G_Foo` as a normal class name and emits `class_name G_Foo` verbatim. Once a project has migrated past the initial GD→TS conversion, `G_Foo` is the canonical identifier on both sides and there is no further round-tripping to track.
- Anonymous-class naming, addon-specific override: when the GD→TS converter runs in addon mode (`GdToTsOptions.isAddon: true`, set by `generateAddonTypings`), anonymous addon scripts use the sentinel `_$CLASS$_` (constant `ANONYMOUS_ADDON_CLASS_NAME` in `src/converter/common/index.ts`) instead of the filename-derived `_FilenameInUpperCamel`. `$` is not a valid GD identifier character, so the sentinel can never collide with a real GD class. Each addon `.ts` is its own ES module, so multiple addon files exporting `_$CLASS$_` don't collide either — consumers see the class through the `import type { _$CLASS$_ as ScriptClass }` alias in the generated `.gd.d.ts`, never by global name.
- Addon `class_name` preservation: with `_$CLASS$_` claiming the "anonymous" slot in addon mode, real `_`-prefixed `class_name` declarations are no longer ambiguous and the `_Foo` → `G_Foo` escape is **bypassed** in addon mode. The escape is non-trivial to reverse and addon class names are external — third-party-owned, globally registered, and referenced by consumer code under that exact name — so renaming would silently break everything. The escape still applies in non-addon GD→TS runs (where `_FilenameInUpperCamel` would otherwise collide with real `_Foo`). Two coordinated changes make this work: `scanScriptClassHeader` returns the raw `class_name` text and the helper `resolveTsClassName` in `emitSourceFile` applies the escape conditionally on `ctx.isAddon`. `scanTsFilesForClasses` takes an `isAddon` flag (default `false`); in addon mode the anonymity test becomes `className === ANONYMOUS_ADDON_CLASS_NAME` so `_Foo` is correctly classified as a NAMED class and emitted into `declare global`. Outside addon mode the legacy `isAnonymousClassName` (any `_`-prefix) still applies.
- Addon-output one-way invariant: addon-mode TS→GD direction is **not supported**. The addon-specific naming rules (`_$CLASS$_` sentinel, `_Foo` preserved verbatim) make the generated `.ts` files asymmetric — both `_$CLASS$_` and a preserved `_Foo` start with `_`, so the TS→GD direction's `isAnonymousClassName` (used in `class-body.ts` and `imports.ts`) would treat them as anonymous and skip emitting `class_name`, producing wrong `.gd`. This is fine in practice: `findTsFiles` (and the watcher / convert-gd discovery) all exclude `addons/`, generated addon `.ts` files carry a `// @ts-nocheck — auto-generated from GDScript addon` header, and addons never enter the TS→GD pipeline. Don't add an addon-aware check to `class-body.ts` / `imports.ts` — keep the asymmetry as a documented invariant rather than introducing a flag every TS→GD call site has to thread through.
