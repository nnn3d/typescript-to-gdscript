# GD → TS converter notes

Edge cases and design decisions for `src/converter/gd-to-ts/` (including its post-conversion helpers and the tree-sitter parser quirks it works around). Rules shared with TS → GD are in `src/converter/AGENTS.md`. The project overview is `PROJECT.md` at the repo root.

- Emit-time IN widening needs a separate `classEnumNames: Set<string>` on `GdToTsContext` (populated alongside `classTypeNames` in `class-scope.ts`) because `classTypeNames` holds BOTH inner class names and enum names, and post-qualification text like `Config.Inner` vs `Config.Status` can't be distinguished without knowing which. Enums are numeric (skip widening); inner classes are reference types (widen). Dotted references where the first segment is a Godot registered class (e.g. `Node.ProcessMode`) are treated as class enums; dotted references where the first segment is in `classTypeNames` AND NOT in `classEnumNames` are treated as inner-class references and widened.
- Phase B (nullable helper, addon mode) uses a text-only classifier `isTextReferenceType` rather than the TS checker because addon .ts files are wrapped in `// @ts-nocheck` and the program used by `generateAddonTypings` has no access to the main project's Godot typings — `checker.getTypeAtLocation()` would return `any` for reference types like `Node`, and widening would never fire. Text-based classification sidesteps this by consulting the registry directly.
- `self.method()` vs `self.callback`: only strip `self.` for method call expressions, not property access as argument
- GD-to-TS `self.` resolution: registry always required, only known members (own + Godot inherited) get `this.` prefix
- GD-to-TS scope: local vars/params shadow class members to prevent incorrect `this.` prefix
- GD-to-TS `new()` (constructor): GDScript instantiates via a hidden static `new()`. `emitAttribute` maps `Receiver.new(args)` → `new <Receiver>(args)`; `emitCall` maps a **bare** `new(args)` (the unqualified self-class constructor) → `new <ctx.className>(args)`. The receiver name is resolved to what's actually in scope in the emitted TS: `qualifyClassType` first (an inner class / class enum lives in the paired `namespace`, so `Blueprint.new()` → `new Factory.Blueprint()`, not the out-of-scope `new Blueprint()`), then `selfClassNameIfMatches` (self class, honoring the `_Foo`→`G_Foo` escape), else verbatim (Godot / other user class). `ctx.className` is the already-escaped TS class name and is swapped to the innermost class inside `withClassScope`, so a bare `new()` inside an inner class resolves to that inner class (and an anonymous script resolves to its filename-derived class name). Skipped when `new` is shadowed by a local variable. (Note: `self.new()` is **invalid** GDScript — `new()` is static on the class, not callable through an instance — so it isn't special-cased.)
- GD-to-TS self-class name escaping: a `class_name _Foo` is emitted as TS class `G_Foo` (`escapeUnderscoreClassName`, non-addon). References to the **self** class must use the escaped name too — `selfClassNameIfMatches()` detects when a type/`.new()` receiver names the current class (via the `_Foo`→`G_Foo` escape) and `escapeSelfClassType()` applies it to mapped type strings. Covers `_Foo.new()` → `new G_Foo()`, return types (`-> _Foo`), params, and var/member type annotations. Scoped to the self class only: other user classes stay verbatim so the batch import-injection pass (keyed on the un-escaped GD name) still resolves them. Anonymous filename-derived names (`_Anonym`) are never `G_`-escaped, so they're unaffected
- GD-to-TS `static func` → TS `static method()`: detected via `isStaticFunction()` (type-inference.ts). ⚠️ tree-sitter-gdscript exposes the keyword as a `static_keyword` **named child** of the `FunctionDefinition` — NOT a `static` field — so `childForFieldName('static')` returns null (unlike variable statements, which DO have a `static` field). The keyword is emitted before any `async` (TS requires `static async`, not the reverse). The same `isStaticFunction()` drives `collectMember` (class-scope.ts), which adds static funcs to `staticMembers` so bare in-class calls emit `ClassName.foo()` (both `emitCall` and `emitExpr` prefix static members with the class name) — required for the emitted `static` method to be reachable
- AST type post-processing: `const enum` → const object (erasableSyntaxOnly), `SyntaxType.X` → `typeof SyntaxType.X` in type positions
- tree-sitter-gdscript `ParametersNode` name clash: type alias renamed to `ParameterChildNode`
- tree-sitter-gdscript comment bug: `#"` (no space) not parsed as comment; workaround adds space after `#`/`##` in `fixCommentIndentation()`
- GD-to-TS: type annotations referencing class enums/inner classes qualified with class name (`State` → `ClassName.State`)
- GD-to-TS match statements (`src/converter/gd-to-ts/match.ts`, split out of `statements.ts` to stay under the 500-line rule; the two import each other — `match.ts` needs `emitBody`, `statements.ts` needs `emitMatchStatement` — which ES modules resolve fine at function-call time): `isSimpleMatchStatement()` checks whether all PatternSections use only literal/expression/wildcard patterns (no Array/Dictionary/PatternBinding/PatternGuard). If so, `emitSimpleMatchAsSwitch()` produces a native TS `switch`/`case`/`default` block with NO `break` (the dialect has none); multi-pattern sections (`1, 2, 3:`) become stacked `case` labels, and an empty section gets a `{}` block so it does not stack onto the next. A `break` inside a match section is an `error` (`breaksThroughMatch()` in `src/converter/gd-to-ts/statements.ts`: the nearest loop-or-match ancestor is a `match`, stopping at a function boundary). GDScript `match` is not breakable, so such a `break` exits the surrounding LOOP — but the `switch` it converts into is breakable, so the same word would exit the branch instead, and TS has no label to name the loop with (GDScript has none either, so the dialect carries none). A `break` belonging to a loop inside the section is emitted normally. Otherwise falls back to `gd.match([...])` with object/arrow-function cases.
- GD-to-TS setget variables: `emitClassVariable()` inspects the `setget` child node. Simple case (no default value, no function-ref syntax) → `emitTsAccessors()` produces a pair of `get`/`set` accessors and synthesizes defaults for whichever side is missing. Complex case (has default value OR uses `get = fn, set = fn`) → `emitGdGetsetCall()` produces `name: T = gd.getset({...})` — always emits the property type annotation to sidestep `TS7022`. The annotation `T` is resolved in this order:
  1. Explicit GDScript type annotation (`var b: int = ...` → `int`)
  2. `typeof <value>` when the value expression is an identifier or attribute access (via `tryEmitTypeofValue` — the GDScript AST node must be `Identifier` or `Attribute`)
  3. Fallback: `unknown` (default) or `any` (when `--unsafe-use-any` is passed)
     Mixing inline bodies with function-reference syntax in one variable is an error.
- GD-to-TS `'''`/`"""` triple-quoted strings as expression statements → `/* */` block comments (both class body and function body)
- GD-to-TS inline comments in expressions (e.g. `# comment` inside function call args) → `/* comment */`
- GD-to-TS `emitAttribute` checks `!ctx.localVars.has()` to prevent incorrect `this.` prefix when local variable shadows class member
- A GD parameter written `x := 1` parses as a TYPED parameter whose type node is the walrus, so reading its text gave `x: := | null = 1`. `declaredTypeNode` in `gd-to-ts/functions.ts` answers null for an `InferredType`, leaving the parameter untyped and letting TypeScript infer from the default exactly as GDScript does — the same treatment `emitTypeAnnotation` already gives locals and members
- A GD `const` inside a FUNCTION BODY is a local binding, not a class member — `emitBody` routes it through `emitLocalVariable` with the `const` keyword. It carries the same `name`/`type`/`value` fields as a `var`, so nothing else differs. The class-scope and file-scope emitters only ever see the class-level ones; before this the local form fell through to `Unhandled GDScript statement: const_statement` and emitted its raw GDScript text
- GD `x not in y` -> `!(x in y)` (`emitBinaryOp`). It is ONE operator spelled in two words, the same shape as `is not`: tree-sitter hangs both words on the node as anonymous children and leaves only `not` in the `op` field. Untreated, that `not` read as the unary operator and the pair emitted as `x ! y` — not valid TypeScript, and reported by nothing. A leading `not` (`not x not in y`) gets the same lift `not X op Y` does — tree-sitter hangs it on `x`, GDScript reads `not (x not in y)` — so it emits `!!(x in y)`, not `!(!x in y)` A leading negation may also be spelled `!`, which GDScript binds exactly like `not` (verified at runtime: `!x == y` is `not (x == y)`); both lifts ask `isNegation`, so `!key in items`, `!key not in items` and `!key == "k"` no longer come out as TypeScript's `(!key) in items` — pinned by `operators` (`bang_*`).
- `not X is Y` negation fix: `emitUnaryOp` wraps binary operator operands (`instanceof`, `gd.is()`) in parentheses when negated, so `not level_info is LevelData` → `!(level_info instanceof LevelData)` instead of broken `!level_info instanceof LevelData`
- `gd.is()` for primitive type checks: `x is int` / `x is float` / `x is bool` / `x is String` convert to `gd.is(x, int)` etc. in TS (since `instanceof` doesn't work with TS type aliases). Class `is` checks still use `instanceof`. Type definition in `gd-helpers.d.ts` with overloads per primitive type.
- Class-keyed dictionaries (GD→TS). The typings make `Dictionary<K, V>` with a string / number key an index signature, and with any other key a method surface (`DictionaryKeyMethods`), and no object literal has its typed `find_key` — so `var by_node: Dictionary[Node, int] = {}` came out TS2322. Two parts fix it. (1) `gd.dict` (hand-kept `typings/globals/gd-helpers.d.ts`) is `<D = Dictionary>(entries: NoInfer<GdDictEntry<NonNullable<D>>>[]) => D`: the whole dictionary type `D` comes ONLY from where it goes, and `GdDictEntry` derives the `[key, value]` shape the entries are checked against — `keyof` separates the string- and number-index forms a `Dictionary<string | int, V>` resolves to, and a `DictionaryKeyMethods<K, V>` surface is matched last, since an index type matches its pattern too. Inferring K and V through the conditional `Dictionary<K, V>` alias does not work for index-signature destinations (TypeScript infers into neither branch), which is why an earlier `DictionaryKeyMethods<K, V>` return type left `var d: Dictionary[String, int] = {key: 1}` at TS2322. Inferring them from the entries was tried and fails: `DictionaryKeyMethods`' key is invariant, so `gd.dict([[this, 1.0]])` inferred `K = this` and was refused as `Dictionary<Node, float>` (a subclass key the same); an overload pair also broke mixed keys into an untyped `Dictionary`. With nowhere typed to go, K = V = unknown, the old untyped result. A second signature, `<K, V>(entries: [NoInfer<K>, NoInfer<V>][]) => Dictionary<K, V>`, takes EXPLICIT key and value types (`gd.dict<Vector2, int>([...])`). It is listed after `<D>`, and TypeScript only considers a signature whose type-parameter count fits the explicit type arguments, so a call without them never reaches it — unlike the broken overload pair above, nothing is inferred from the entries. Pinned by `tests/typings/type-checks/gd-helpers.ts` (explicit, wrong key, wrong value, and the destination and mixed-key cases unchanged) and the `dict` ts-to-gd fixture. (2) The post-pass helper `empty-dict` (`gd-to-ts/helpers/empty-dict.ts`, run after `explicit-convert`) rewrites each `{}` TypeScript refuses as a `DictionaryKeyMethods` (TS2322 / TS2345) to `gd.dict([])`, in any position — field, local, parameter default, assignment, return, argument. Which `{}` qualifies is read from the diagnostic's code, the node and its contextual type, never from the message text, which varies across TypeScript versions and locales. `assignedValueNode` (shared with `explicit-convert`) finds the value a diagnostic is about when it spans a name, a whole parameter (TypeScript reports a default's error across the declaration) or `return`. Making `{}` itself assignable was tried too: the only blocker is the plain-object `Object.find_key` generic, and a return-only type parameter that satisfies it lets `o.find_key(1)` be typed as whatever the caller declares — unsound. Pinned by `tests/fixtures/ts-helpers/default/empty-dict`, `tests/typings/type-checks/gd-helpers.ts` (`test_typed_dict`), and the gd-to-ts `dict-generics` fixture through the converted-project test. TS→GD still emits every dictionary annotation as a plain `Dictionary` (typed dictionaries stay TS-side)
- GD-to-TS implicit base (`implicitBase` in `gd-to-ts/context.ts`): a class with no `extends` has Godot's `RefCounted` as its base. The TS side already said so (`extends RefCounted`, script and inner classes), but the inherited-member lookup ran only when an `extends` was written, and `resolveAllInheritedMembers` stopped at a user base class with none — so `get_reference_count()`, `CONNECT_ONE_SHOT`, `NOTIFICATION_PREDELETE` stayed bare there (TS2304). Both the emitted `extends` and the lookup now go through `implicitBase`. An inner class's inherited CONSTANT still fails, as TS2576 rather than TS2304: the StaticProps merge that makes `this.CONST` valid exists only for the script class. Pinned by the gd-to-ts `implicit-base` / `implicit-base-child` fixtures
- GD-to-TS engine class enums (`gdTypeToTs`, `gd-to-ts/type-inference.ts`): a dotted type naming an enum of an engine class (`Node.ProcessMode`, `Control.LayoutPreset`, including one reached through a subclass — `GodotClassRegistry.isClassEnum` walks the chain — or through a SCRIPT class that inherits it, `EnemyBase.MotionMode`, which `isEngineClassEnum` follows through the user-class index to its engine base unless a script on the way declares that name itself) becomes `int`. The typings declare such an enum only through its values (`static readonly PROCESS_MODE_INHERIT: int`), never as a type, so `Node.ProcessMode` in TS was TS2702 in every position — annotations, params, returns, signal args, `Array[...]` inners. Global enums (`Variant.Type`) are declared and stay as written; user enums resolve through the paired namespace. `gdTypeToTs` takes the registry for this; every caller passes `ctx.registry`. Pinned by the gd-to-ts `inherited-constants` fixture (`mode`, `preset_for`), type-checked by the converted-project test
- GD-to-TS dictionaries (`gd-to-ts/expressions.ts`): a Lua-style pair (`{hp = 3}`) names its key — Godot 4.7 stores it as the StringName `&"hp"` (verified at runtime: `typeof` is `TYPE_STRING_NAME`) — so it is emitted exactly like `{&"hp": 3}`, as the computed key `[StringName('hp')]`. It used to be read as an identifier key, and `{hp = 3}` became `gd.dict([[hp, 3]])`, which reads a variable `hp` — a different key, or no binding at all. Godot rejects a dictionary that mixes the two styles, so a Lua pair never shares the `gd.dict` path with a variable key. Pinned by the gd-to-ts `dict` fixture (`lua`)
- GD-to-TS comma lists (`emitCommaList` in `gd-to-ts/expressions.ts`, used by call arguments, `.new()` arguments and array literals) fold an interleaved `#` comment onto the item it TRAILS. GDScript allows a comment between the arguments of a call spread over several lines; tree-sitter makes it a sibling of the values, so emitting the list position by position produced `f(a, /* note */, b)` — not valid TypeScript. It attaches to the preceding value rather than being dropped, which keeps both the text and what it describes; a list that OPENS with a comment has nothing to attach to, and that one is dropped
- GD-to-TS extras (`src/converter/gd-to-ts/syntax-children.ts`): the grammar declares `\` line continuations and `#` comments as extras, which may sit between any two tokens and hang on whichever node encloses that spot. Reading a value as `namedChildren[0]` after a keyword or bracket took the extra instead, and `return \` + newline + `a + b` came out as `return /* ERROR: Unhandled GDScript expression: line_continuation */`. `firstSyntaxChild()` skips extras at those reads — `return` (and a lambda's one-line `return`), `await`, `not`/`-`/`+`/`~` (also the lifted `not … in` / `not X op Y` operands), `(…)`, `[…]` keys, match `when` and `var` bindings, and the three `extends` readers (script header, `parseGdClassInfo`, inner classes). `syntaxChildren()` filters them from a match section's pattern list (`1, \` + newline + `2:`, on both the `switch` and the `gd.match` path), an attribute chain (`n \` + newline + `.name`) and an array pattern; `emitCommaList` drops continuations and keeps its comment folding. A comment that OPENS a bracket (`(` newline `# note` newline `a)`) is dropped the same way — before, it replaced the value. A TYPE split over lines (`Array[\` + newline + `int]`) is read through `typeSourceText()`, the type's text with both extras removed and its whitespace collapsed: the raw `.text` put the `\`, the line break and the indentation into the TS annotation, and a split `Object` missed its `GodotObject` rename. Every GD→TS read of a type node's text goes through it; a string `extends` target (a script path) comes back as written, since a `#` or a run of spaces there is part of the path. Positions where the value comes first (a call's callee, an expression statement, a binary operand read by field) never had the problem. Pinned by the gd-to-ts `line-continuations` fixture, with `line-continuations-base.gd` (no `.ts` pair) supplying the cross-file `extends`; every site listed here fails that fixture when reverted to `namedChildren[0]`
- GD-to-TS ts-helpers console logging: logs phase names, pass counts, and fix counts during conversion for debugging/observability
- A GDScript global used as a VALUE rather than called (`var c: Callable = typeof`, which Godot accepts) is reported by GD→TS, not converted. Neither spelling works: the bare name is a TS syntax error, and `gd.typeof` is a property read that converts back to `gd.get("typeof")`. Note `gd.<helper>` in value position is a separate, pre-existing gap — `gd.dict` / `gd.as` also emit `gd.get("...")` with no diagnostic
